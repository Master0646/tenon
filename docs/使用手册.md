# DevFlow 使用手册

让 AI 编码 Agent 先出方案、经你批准再改代码，并把需求和设计原因留在仓库里。

> 适用版本：devflow 0.2.0　·　更新：2026-11-08　·　本手册的输出示例均来自 0.2.0 实测；`approve`、`archive`、`evidence confirm` 只能由人运行，它们的输出按源码 `src/cli.ts` 核对。

DevFlow 嵌入你已有的 Agent（Claude Code 或 Codex）使用，自己不调用任何模型。Agent 负责读代码、写方案、写代码；`devflow` 命令只做确定性的事：校验格式、给批准绑定哈希、计算状态、运行验证命令、合并规范、在提交时把关。

> **只负责审查和批准？** 你只需要读[快速入门](#快速入门)的第 1 步，以及[第 2 步：审查](#第-2-步审查人)、[第 3 步：批准](#第-3-步批准人在自己的终端)和[第 8 步：归档](#第-8-步归档人在自己的终端)。其余工作由 Agent 完成。

**一句话流程**

```text
提方案(Agent) → 审查并批准(人) → 实现、验证、记证据(Agent) → 提交代码(人) → 更新知识页(Agent) → 归档(人)
```

## 选择你的 Agent

两种 Agent 的用法相同，区别在于调用技能的方式和安全防线的强度。

| | Claude Code | Codex |
| --- | --- | --- |
| 调用技能 | 直接说技能名："用 devflow-propose 提一个变更" | 用 `$devflow-propose` |
| 生成的文件 | `.claude/skills/devflow-*/`、`CLAUDE.md`、`.claude/settings.json` | `.agents/skills/devflow-*/`、`AGENTS.md`、`.codex/rules/devflow.rules` |
| 禁止 Agent 运行 approve / archive | 有效（已实测拦截） | 实验性：项目被信任后才加载规则 |
| 交互终端防线 | 有效：Agent 的 shell 不是交互终端 | **可被绕过**：模型可以自行申请交互终端 |

两个都用也可以，`devflow init` 会为两者都生成文件。

## 快速入门

做完这一节，你会有一个启用了 DevFlow、提交门禁生效、能跑验证命令的项目。大约 5 分钟。

**前提**：Node 22 或更高版本，git，以及一个**至少已有一次提交**的 Git 项目。

### 1. 安装 devflow

在 devflow 源码目录里打包，然后全局安装：

```bash
npm install && npm pack
```

```bash
npm install -g ./devflow-0.2.0.tgz
```

```bash
devflow --version
```

预期输出：

```text
0.2.0
```

必须全局安装：终端里要能运行 `devflow`，pre-commit hook 也依赖这个命令。

> 开发 devflow 本身时，可以不打包，直接运行 `node src/cli.ts <命令>`（需要 Node 23.6 或更高版本）。

### 2. 在项目里初始化

在你的项目根目录运行：

```bash
devflow init
```

预期输出（节选）：

```text
+ .devflow/project.yaml
+ .devflow/specs/specs.lock
+ .devflow/knowledge/index.md
+ .gitignore（追加 .devflow/runtime/）
✓ pre-commit hook 已安装：/path/to/project/.git/hooks/pre-commit
✓ .claude/skills/devflow-propose/SKILL.md
✓ CLAUDE.md
✓ .claude/settings.json
…
```

`init` 只为检测到的 Agent 生成文件：项目里有 `.claude/` 或 `CLAUDE.md`，就装 Claude Code；有 `.codex/`、`.agents/` 或 `AGENTS.md`，就装 Codex。两种都没检测到时，两个都装。要指定，写 `--agents claude`、`--agents codex` 或 `--agents claude,codex`。

`init` 可以重复运行，不会覆盖已有文件。`CLAUDE.md` 和 `AGENTS.md` 里，只有 `<!-- devflow:begin -->` 和 `<!-- devflow:end -->` 之间的内容由 DevFlow 维护，其余内容不会被改动。

> **注意**
> 项目里已经有别的 pre-commit hook 时，`init` 不会覆盖它，而是提示你手动加一行。

### 3. 声明验证命令（人来做）

编辑 `.devflow/project.yaml`，把 `verify: []` 换成你平时用来确认"没改坏"的命令：

```yaml
verify:
  - name: unit-tests     # 名称，不能重复；任务的验收条件会用这个名字引用它
    run: npm test        # 用 sh -c 执行
  - name: backend-test
    run: mvn -q -B test
    cwd: backend         # 可选，相对项目根目录
```

> **注意**
> 只有这里声明的命令会被 `devflow verify` 运行，所有命令退出码为 0 才算通过。这个文件由人维护，并计入每次批准的哈希：如果 Agent 能改它，就能删掉测试让自己通过。所以批准之后改动它，已有的批准会失效。

常见技术栈：

| 技术栈 | `run` |
| --- | --- |
| Node | `npm test`；前端没有测试时，至少配 `npm run build` |
| Maven | `mvn -q -B test`（`-B` 关闭交互输出） |
| Gradle | `./gradlew test --console=plain` |
| Python | `pytest -q` |
| Go | `go test ./...` |

验证命令生成的文件（`dist/`、`target/`、`node_modules/` 等）必须写进 `.gitignore`。否则验证期间工作树发生变化，结果会被记为 `unknown`。

### 4. 验证你的安装

```bash
devflow doctor
```

预期输出：

```text
✓ Node：v26.13.0
✓ git：git version 2.39.5
✓ 仓库：/path/to/project
✓ 初始化：.devflow/ 存在
✓ hook：指向 /opt/homebrew/lib/node_modules/devflow/dist/cli.js
✓ Agent 文件（claude）：与当前版本一致
! 知识页：知识页为空，devflow-archive 没有页面可更新
    修复：用 devflow-scan 技能生成知识页；小项目可以跳过
✓ .gitignore：已忽略 .devflow/runtime/
```

`✓` 表示正常，`!` 表示警告，`✗` 表示错误。有 `✗` 时退出码为 1，每个问题下面都附有修复命令。知识页为空的警告可以先不管，见[可选：生成知识页](#可选生成知识页)。

**如果出现以下问题**

- `! project.yaml：没有声明验证命令`：回到第 3 步。不声明验证命令时，验证结果永远是 `unknown`，变更无法归档。
- `✗ hook：…不存在`：devflow 的安装位置变了，重新运行 `devflow init`。
- `✗ Agent 文件…不一致`：运行 `devflow update`。

### 5. 提交

```bash
git add -A && git commit -m "启用 DevFlow"
```

预期输出中会有一行，表示提交门禁已经生效：

```text
✓ devflow check 通过
```

> 使用 Codex 时，第一次在项目里打开 Codex 要选择**信任**该项目，`.codex/rules/` 才会加载。

## 走一遍完整的变更

下面以一个最小的需求为例：给 `math.js` 新增 `subtract(a, b)`。每一步都标明由谁来做。

### 第 1 步：提方案（Agent）

在 Agent 里说：

> 用 devflow-propose 提一个变更：在 math.js 中新增 subtract(a, b)，返回 a 减 b。

Agent 信息不足时会先问你，然后读相关代码和当前规范，运行 `devflow new <id>` 生成目录，写好方案，最后运行 `devflow validate` 和 `devflow render`。**这一步 Agent 不会改业务代码。**

Agent 生成的变更目录如下：

```text
.devflow/changes/2026-11-08-add-subtract/
├── change.yaml            标题与影响路径
├── proposal.md            为什么、改什么、影响、不做什么
├── specs/math/spec.md     规范增量：本次对系统行为契约的增、改、删
├── design.md              技术方案与流程图
└── tasks.yaml             任务、依赖与验收条件
```

其中 `tasks.yaml` 是后面验收的依据，每条验收条件都要写清楚怎么证明：

```yaml
schema_version: 2
tasks:
  - id: T1
    title: 实现 subtract 并补测试
    acceptance:
      - id: AC1
        text: subtract(5, 3) 返回 2
        method: automated      # automated：由验证命令证明；manual：由人确认
        check: unit-tests      # 引用 project.yaml 中的 verify.name
```

**验证**：Agent 最后会给出 render 的结果。

```text
✓ /path/to/project/.devflow/runtime/rendered/2026-11-08-add-subtract.html
  内容哈希：sha256:79445fe7ed97bef5475cec4400d48d5e7ece7c1f033f7997691a9db2a89bc446
  审查后由人在自己的终端运行：devflow approve 2026-11-08-add-subtract
```

### 第 2 步：审查（人）

用浏览器打开上面的 HTML 文件。审查页直接从方案文件生成，没有经过模型改写，离线可用。

| 面板 | 内容 |
| --- | --- |
| A 提案 | 为什么、改什么、影响、不做什么 |
| B 规范增量 | 新增（绿）、修改（黄）、删除（红）的需求，每条需求附场景表（WHEN / THEN） |
| C 设计 | 技术方案与流程图 |
| D 任务与依赖 | 每个任务的验收条件和依赖图 |
| E 被审文件与内容哈希 | 验证命令、每个文件的哈希，以及可以直接复制的批准命令 |

重点看三处：

1. 验收条件能不能真正被验证？`automated` 的条件引用的是哪个验证命令？
2. `affected_paths` 有没有覆盖要改的代码？
3. "不做什么"是否符合你的预期？

**要修改时**，直接告诉 Agent 改哪里。Agent 会重新校验、重新生成审查页，哈希也会随之变化。

### 第 3 步：批准（人，在自己的终端）

复制审查页 E 面板末尾的命令，在你自己的终端里运行：

```bash
devflow approve 2026-11-08-add-subtract --hash 79445fe7ed97
```

`--hash` 至少要有 12 位。它和当前内容一致时直接批准，不会再让你输入 `y`。预期输出：

```text
变更：2026-11-08-add-subtract
基线：a1b2c3d  批准人：你的名字
内容哈希：sha256:79445fe7ed97…
被审文件：
  .devflow/changes/2026-11-08-add-subtract/change.yaml
  …
✓ 已批准 2026-11-08-add-subtract
下一步：在 Agent 里说"用 devflow-apply 实现变更 2026-11-08-add-subtract"
```

只有看到 `✓ 已批准` 才算成功。

不带 `--hash` 时，终端会列出同样的信息并要求确认。核对哈希和审查页一致后，输入 `y` 并回车。

**如果批准不成功**

| 提示 | 原因与处理 |
| --- | --- |
| `--hash 与当前内容哈希不一致，未批准` | 审查之后方案又被改过，或者命令没复制完整。重新 render，从新页面复制命令 |
| `approve 只能由人在交互终端中运行` | 命令在非交互环境中运行，例如被 Agent 代为执行、在编辑器任务面板里运行或经过管道。请在普通终端窗口里运行 |
| `✗ 未批准：… 状态仍为 draft` | 确认时没有输入 `y`。重新运行 |
| 未配置 git user.name | 运行 `git config user.name "你的名字"`，批准人取自这里 |

### 第 4 步：实现并验证（Agent）

在 Agent 里说：

> 用 devflow-apply 实现变更 2026-11-08-add-subtract。

Agent 会先记录开工：

```bash
devflow apply 2026-11-08-add-subtract --start
```

```text
✓ 2026-11-08-add-subtract 已开工（基于 a1b2c3d）
```

然后写代码和测试，运行验证命令：

```bash
devflow verify 2026-11-08-add-subtract --json
```

```json
{
  "result": "pass",
  "checks": [{ "name": "unit-tests", "log_hash": "sha256:…", "exit": 0, "ms": 412, "log": ".devflow/runtime/verify/…" }],
  "run_id": "6f1c…"
}
```

> **注意**
> 下一步记录证据时要用到 `run_id`，它只在 `--json` 输出里出现。不加 `--json` 时，输出是 `✓ unit-tests  退出码 0  0.4s`，后面跟一行"配置检查结果"。

Agent 发现方案本身有问题时，会停下来告诉你，而不是自己改方案。改方案会让批准失效，需要你重新批准。

### 第 5 步：记录验收证据（Agent，人工项由人确认）

测试通过，不等于验收条件被覆盖了。每条验收条件都需要一份证据，说明它是由哪个测试、哪条断言证明的。Agent 写一个 JSON 文件：

```json
{
  "task": "T1",
  "acceptance": "AC1",
  "kind": "automated",
  "summary": "subtract(5, 3) 返回 2",
  "verify_run": "6f1c…",
  "check": "unit-tests",
  "test": "test/math.test.js",
  "assertion": "assert.equal(subtract(5, 3), 2)",
  "artifacts": []
}
```

```bash
devflow evidence add 2026-11-08-add-subtract --file AC1-evidence.json
```

命令会输出记录下来的证据，其中包含 `evidence_id`。

自动证据必须满足三个条件，否则会被拒绝：引用的是**本轮批准之后**、**当前代码版本下**、**指定检查通过**的那次验证。

**人工验收项**（`method: manual`）的证据，把 `kind` 改成 `manual`，并填写 `procedure`（怎么操作）、`expected`（预期）、`observed`（实际看到的）。Agent 记录之后，**由你在自己的终端里确认**：

```bash
devflow evidence confirm 2026-11-08-add-subtract <evidence-id>
```

所有验收条件都有有效证据后，Agent 标记任务完成：

```bash
devflow task done 2026-11-08-add-subtract T1
```

```text
✓ T1 已完成；任务 1/1
```

**验证**：任何时候都可以运行 `resume`，查看还缺什么以及下一步做什么。

```bash
devflow resume 2026-11-08-add-subtract
```

```text
2026-11-08-add-subtract: ready_to_archive — 验证通过，等待人工归档
下一步：devflow archive 2026-11-08-add-subtract
```

**如果证据被拒**

| 提示 | 处理 |
| --- | --- |
| `自动证据必须引用本轮批准、当前代码下成功的指定验证检查` | 验证之后代码又变了，或者 `check` 名称和验收条件里写的不一致。重新运行 `verify --json`，用新的 `run_id` |
| `证据方式与批准的验收条件不一致` | `kind` 必须和验收条件的 `method` 一致 |
| `任务验收条件不存在：T1/AC9` | `task` 或 `acceptance` 写错了，对照 `tasks.yaml` |
| `当前状态不允许记录证据` | 还没开工，或者批准已经失效。运行 `devflow resume` 看原因 |
| `任务 T2 依赖的任务尚未完成` | 先完成被依赖的任务，并补齐它的证据 |

### 第 6 步：提交代码（人）

什么时候提交、提交信息怎么写，由你决定。DevFlow 不会自动提交或推送。

提交时，把变更目录 `.devflow/changes/<id>/` 和证据目录 `.devflow/evidence/<id>/` 一起提交。其中的 `events.jsonl` 是批准、验证和证据的记录。

> **注意**
> 验证结果绑定当时的工作树内容（不含 `.devflow/`）。验证之后改了任何文件，包括文档，状态都会回到 `applying`，证据也会失效，需要重新验证并重新记录证据。所以说明文档要在 verify 之前写完。

### 第 7 步：归档准备（Agent）

在 Agent 里说：

> 用 devflow-archive 为变更 2026-11-08-add-subtract 做归档准备。

Agent 会更新相关的知识页，链接到归档后的设计文档，并确认 `devflow wiki lint` 没有错误。项目里没有知识页时，可以跳过这一步。

### 第 8 步：归档（人，在自己的终端）

```bash
devflow archive 2026-11-08-add-subtract
```

终端会列出将要写入的规范文件和将要移动的目录。确认后输入 `y`：

```text
变更：2026-11-08-add-subtract  归档人：你的名字
将写入：
  .devflow/specs/math/spec.md
将移动：.devflow/changes/2026-11-08-add-subtract → .devflow/changes/archive/2026-11-08-add-subtract
确认归档？输入 y 确认：y
✓ 已归档到 .devflow/changes/archive/2026-11-08-add-subtract；更新规范：.devflow/specs/math/spec.md
```

然后提交归档结果：

```bash
git add -A && git commit -m "归档 2026-11-08-add-subtract"
```

一个功能因此分成两次提交，这是有意的：知识页的 `verified_commit` 要指向包含代码改动的那次提交，所以代码必须先提交。

归档中途被打断时，再运行一次 `devflow archive <id>` 即可。它会发现未完成的事务，从中断处继续，不会重复写入。

### 之后

在任何新会话里都可以问：

> subtract 是哪次变更加的？为什么不处理非数字输入？

Agent 会从 `.devflow/changes/archive/` 和 `.devflow/specs/` 里找到需求、规范和设计原因，并给出出处。

## 状态与下一步

状态不存盘，每次都由变更文件、`events.jsonl` 和 git 现算。查看状态：

```bash
devflow status                 # 所有进行中的变更
devflow status <id>            # 一个变更
devflow status --all           # 同时列出已归档的变更
devflow resume <id>            # 一个变更：状态、证据缺口和下一条命令
```

```text
2026-11-08-add-subtract  draft  任务 0/1  尚未批准
```

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `draft` | 尚未批准，或者批准后被审文件被改过 | 人审查后 `approve` |
| `rebase_required` | 已批准、未开工，但批准后有提交改动了 `affected_paths`，或者同一能力的规范变了 | 人重新评估方案，必要时让 Agent 修改，再 `approve` |
| `approved` | 已批准，可以开工 | Agent 用 devflow-apply 实现 |
| `applying` | 已开工；任务未完成、证据失效，或者验证之后代码有改动 | Agent 继续实现，或者重新 `verify` 并补证据 |
| `needs_fix` | 最近一次验证结果为 `fail` 或 `unknown` | 看验证日志修复后重新 `verify` |
| `ready_to_archive` | 任务全部完成，证据有效，且验证通过的就是当前代码 | 人提交代码 → Agent 做归档准备 → 人 `archive` |
| `archived` | 已归档 | — |

规则：

- **改方案就要重新批准**：批准后改动任何被审文件或 `project.yaml`，状态回到 `draft`。
- **重新批准就是新的一轮**：之前的开工、验证、证据和任务完成记录都不再算数。
- **`unknown` 不算通过**：以下情况结果都记为 `unknown`：验证命令无法运行、超时（单条命令 30 分钟）、没有声明命令、验证期间工作树发生变化。
- **一个工作树同时只能开工一个 v2 变更**。要并行做多个变更，用独立的 git worktree。

### 按场景检查验证结果

| 场景 | `verify` 结果 | 状态 |
| --- | --- | --- |
| 所有命令退出码为 0 | `pass` | 补齐证据并完成任务后，变为 `ready_to_archive` |
| 任一命令退出码非 0 | `fail`，并输出日志路径 | `needs_fix` |
| 没有声明验证命令 | `unknown` | `needs_fix` |
| 命令不存在，例如没装 `mvn` | `unknown` | `needs_fix` |
| 构建产物没被忽略，验证期间工作树变了 | `unknown` | `needs_fix` |
| 验证通过后又改了代码 | 上次的结果作废 | `applying` |

验证日志在 `.devflow/runtime/verify/<id>/` 目录下。

---

## 可选：生成知识页

知识页（`.devflow/knowledge/pages/*.md`）记录代码"现在是怎样"，每条事实都带源码出处。在 Agent 里说：

> 用 devflow-scan 为本项目生成知识页。

Agent 会按业务模块写页面，并运行 `devflow wiki lint`，直到没有错误。

> **注意**
> 小项目可以跳过这一步。在一个 25 个文件的演示项目上评测，有没有知识页，回答准确率相同，而且有知识页时每题多用约 25% 的轮数。知识页的价值在于代码里看不出来的东西：设计原因、历史变更，以及 Agent 读不完的大项目。

## 可选：本地使用记录

`init` 之后，项目默认在本地记录 devflow 命令的使用情况：命令名（白名单内）、结果、原因码和耗时。不记录完整参数、输出、环境、用户名或源码，也不上传。原始记录保留 30 天，反馈保留 90 天，报告保留 180 天。

```bash
devflow usage configure --off             # 关闭
devflow usage configure --on              # 打开
DEVFLOW_USAGE=off devflow status          # 只对这一次命令关闭
devflow usage report --since 2026-11-01   # 本地报告
devflow usage feedback <id> --file feedback.json
devflow usage export --since 2026-11-01 --out summary.json
devflow usage prune --before 2026-10-01
```

反馈文件格式为 `{category, impact, note, related_invocation?}`，其中 `category` 取 `blocked`、`confusing`、`false-positive`、`missed-defect` 或 `other`。`note` 是自由文本，默认不会出现在聚合导出里；不要在里面写凭据。

关闭记录或记录写入失败，都不影响命令本身的退出码。

## 可选：改进候选与评测

同一类问题出现至少 3 次，会生成一个去重后的改进候选。候选只会生成一份待补全的提案，不会自动审批或实施。

```bash
devflow improve list
devflow improve draft <candidate-id> <change-id>
devflow eval run --suite workflow --out regression.json
devflow eval compare baseline.json regression.json
devflow improve resolve <candidate-id> --report comparison.json
```

故障评测在临时仓库里运行。只有每个任务每个版本至少跑 5 次、关键结果不退化、目标中位指标下降至少 10% 时，才标记为 `improved`，而且这仍不代表统计显著。真实 Agent 评测需要显式启动，可能消耗账号额度。

## 可选：继续使用 v1 格式

0.2.0 新建的变更默认是 v2 格式（`schema_version: 2`，验收条件带证据）。旧的 v1 变更可以继续使用。要显式创建 v1 格式：

```bash
devflow new <id> --schema 1
```

已有 v2 变更的项目，不能再用旧版 CLI 往里追加事件。

## 命令参考

所有命令都支持 `--json`，输出机器可读的结果。出错时退出码为 1，`✗` 后面给出原因和修复提示。标 **人** 的命令要求交互终端，Agent 无法代为运行。

| 命令 | 谁运行 | 说明 |
| --- | --- | --- |
| `devflow init [--agents claude,codex]` | 人 | 创建 `.devflow/`、安装 hook、生成 Agent 文件。可以重复运行 |
| `devflow update [--agents …]` | 人 | 升级 devflow 后重新生成 Agent 文件；不写 `--agents` 时更新已安装过的 |
| `devflow doctor` | 任意 | 自检，并给出修复命令 |
| `devflow new <id> [--schema 1]` | Agent | 生成变更目录骨架。id 用小写字母、数字、连字符，建议 `<日期>-<英文短名>` |
| `devflow validate <id>` | Agent | 校验文件、对当前规范试算合并，并检查审查页会拒绝的写法，报错定位到行号 |
| `devflow render <id> [-o 文件]` | Agent | 生成离线审查页，默认在 `.devflow/runtime/rendered/<id>.html` |
| `devflow approve <id> [--hash 前缀]` | **人** | 批准并绑定内容哈希 |
| `devflow apply <id> --start` | Agent | 记录开工，只能从 `approved` 开始 |
| `devflow verify <id>` | Agent | 运行 `project.yaml` 中的命令；全部通过时退出码为 0 |
| `devflow evidence add <id> --file <json>` | Agent | 记录一条验收证据 |
| `devflow evidence confirm <id> <evidence-id>` | **人** | 确认人工验收证据 |
| `devflow task done <id> <任务>` | Agent | 记录任务完成；依赖的任务必须先完成，证据必须有效 |
| `devflow resume <id>` | 任意 | 当前状态、证据缺口和下一条命令 |
| `devflow status [id] [--all]` | 任意 | 状态、任务进度和原因 |
| `devflow archive <id>` | **人** | 合并规范增量、更新 `specs.lock`、移动变更目录；中断后重跑即可继续 |
| `devflow wiki lint` | Agent | 校验知识页的引用和链接，并检查是否过期 |
| `devflow check [--staged]` | hook / CI | 门禁检查 |

## 文件格式参考

### project.yaml（人维护）

```yaml
schema_version: 1
verify:                  # devflow verify 只运行这里的命令
  - name: unit-tests     # 不能重复
    run: npm test        # 用 sh -c 执行
    cwd: .               # 可选，相对仓库根目录
exclude:                 # 知识页和证据不得引用的文件，规则同 .gitignore
  - ".env*"
  - "**/*.pem"
  - "**/*.key"
  - "**/node_modules/**"
enforce: warn            # warn | strict：暂存了未开工变更的代码时，警告还是拒绝提交
```

### change.yaml

```yaml
schema_version: 2
min_cli_version: 0.2.0
title: 新增减法函数
affected_paths:          # 本变更会改动的代码（glob），不能写 .devflow/ 下的路径
  - math.js
  - test/**
```

`affected_paths` 有两个用途：批准后有提交改动了这些路径时，状态变为 `rebase_required`；提交未开工变更的这些文件时，门禁会警告。

### proposal.md

写四节：`## 为什么`、`## 改什么`、`## 影响`、`## 不做什么`。不能只有标题没有正文。超过 3 句的段落，validate 会给出警告。

### 规范增量 specs/<能力>/spec.md

```markdown
## ADDED Requirements

### Requirement: 减法
系统 SHALL 导出 subtract(a, b)，返回 a 减 b 的结果。

#### Scenario: 整数相减
- WHEN 调用 subtract(5, 3)
- THEN 返回 2

## MODIFIED Requirements
### Requirement: <当前规范中已有的名称>
（这条需求修改后的全文）

## REMOVED Requirements
### Requirement: <当前规范中已有的名称>
**Reason**: 删除原因
```

- 能力名（目录名）只能用小写字母、数字、连字符。
- 每条新增或修改的需求都必须含 `SHALL`、`MUST` 或"必须"，并且至少有一个 `#### Scenario:`。
- 新能力只能用 ADDED，可以加一节 `## Purpose` 说明这个能力是什么。
- MODIFIED 和 REMOVED 里的名称，必须和当前规范完全一致。
- 不改变对外行为的变更（例如纯重构）可以不写规范增量。validate 只会提醒，不算错误。

### tasks.yaml（v2）

```yaml
schema_version: 2
tasks:
  - id: T1
    title: 实现 subtract 并补测试
    acceptance:
      - id: AC1
        text: subtract(5, 3) 返回 2
        method: automated        # automated | manual
        check: unit-tests        # automated 必填，引用 verify.name
  - id: T2
    title: 更新使用说明
    depends_on: [T1]
    acceptance:
      - id: AC2
        text: README 示例可以照抄运行
        method: manual
```

- 任务 id 以字母开头，不能重复。`depends_on` 引用的任务必须存在，依赖不能成环。
- 验收条件的 id 在整个变更内唯一。
- **不要写进度字段**（如 `status`、`done`）。进度记在事件日志里；写在这个文件里的话，每勾选一次任务，批准就会失效一次。

> **注意**
> 在 0.2.0 中，`devflow new` 生成的 `tasks.yaml` 骨架里，注释示例仍是 v1 写法（`acceptance: [字符串]`）。请按上面的 v2 对象格式写。

### execution.md

可选的实施笔记。它是变更目录里唯一不参与批准哈希的文件，改它不会让批准失效。

### design.md 与审查页的写法限制

流程图写在代码块里：

````markdown
```flow TB
(开始) -> {a、b 都是数字?}
{a、b 都是数字?} -> 返回 a - b: 是
{a、b 都是数字?} -> 行为未定义: 否
```
````

- `A -> B: 标签`：冒号后面是连线上的标签。`{条件?}` 是判断节点，`(开始)` 是起止节点。
- 可用的图：`flow`、`sequence`、`tree`、`er`。
- 普通代码块只写语言名，例如 ` ```java `。

审查页会**拒绝**以下写法：`html` 和 `svg` 代码块、带属性的代码块（如 ` ```ts src=… `）、`:::` 块、图片。正文里的 `<` 和 `>` 会被转义，按原样显示。validate 通过，render 就不会因为写法问题失败。

### 证据 JSON

| 字段 | automated | manual | 说明 |
| --- | --- | --- | --- |
| `task`、`acceptance` | 必填 | 必填 | 对应 `tasks.yaml` 中的 id |
| `kind` | `automated` | `manual` | 必须和验收条件的 `method` 一致 |
| `summary` | 必填 | 必填 | 一句话结论 |
| `verify_run` | 必填 | — | `verify --json` 输出的 `run_id` |
| `check` | 必填 | — | 和验收条件的 `check` 一致 |
| `test` | 必填 | — | 测试文件路径，必须在仓库内 |
| `assertion` | 必填 | — | 证明这条验收条件的断言 |
| `procedure`、`expected`、`observed` | — | 必填 | 操作步骤、预期、实际 |
| `artifacts` | 可选 | 可选 | 最多 10 个仓库内文件，每个不超过 1 MiB；不能是 exclude 中的文件，也不能是符号链接 |

附件会被复制到 `.devflow/evidence/<id>/<evidence-id>/`，并记录哈希。附件被改动或丢失，证据就会失效。

### events.jsonl

每行一个事件，记录批准、开工、验证、证据、任务完成和归档。**只能由 devflow 命令追加**。已提交的行被改动或删除时，提交会被门禁拒绝。

### 知识页 knowledge/pages/<slug>.md

```markdown
---
schema_version: 1
title: 数学工具
verified_commit: "9f3a2c1"
sources:
  - path: math.js
    symbol: subtract
  - path: test/math.test.js
    lines: [1, 10]
related_specs: []
---

# 数学工具
……
```

- `verified_commit` **要加引号**：`1234567` 这样的短哈希不加引号，会被 YAML 当成数字读取。
- `symbol` 写成 `类名` 或 `类名#方法名`，必须和源码里的文字一致。
- 正文里用完整路径引用的文件，也要列进 `sources`。漏列的文件改了，这页不会被标为过期。
- 每个页面都要在 `knowledge/index.md` 里有一行：`- [标题](pages/<slug>.md) — 摘要`。

`devflow wiki lint` 报**错误**的情况：frontmatter 缺失或字段不合法；引用的文件不存在、符号找不到或行号越界；引用了 `exclude` 中的文件；`index.md` 漏列页面或列了不存在的页面；正文链接指向不存在的目标。报**警告**的情况：引用的文件在 `verified_commit` 之后有改动；正文引用了没列入 `sources` 的文件；一个知识页都没有。

## Agent 技能参考

`devflow init` 为每个 Agent 安装五个技能。

| 技能 | 什么时候用 | 典型说法 |
| --- | --- | --- |
| `devflow-propose` | 新功能、行为修改、修复，先出方案 | "用 devflow-propose 提一个变更：……" |
| `devflow-apply` | 实现已批准的变更，并验证、记录证据 | "用 devflow-apply 实现变更 <id>" |
| `devflow-archive` | 验证通过后、归档前，更新知识页 | "用 devflow-archive 为变更 <id> 做归档准备" |
| `devflow-scan` | 生成或修复知识页 | "用 devflow-scan 生成知识页" |
| `devflow-ask` | 带出处回答关于项目的问题 | "X 在哪里实现？"（不说技能名也会用到） |

## 提交门禁

pre-commit hook 运行 `devflow check --staged`。CI 中可以运行 `devflow check`，检查工作树。

| 规则 | 结果 |
| --- | --- |
| `.devflow/` 下的文件格式错误 | 拒绝提交 |
| `.devflow/specs/` 和 `specs.lock` 不符（手改、手加、手删） | 拒绝提交 |
| `events.jsonl` 中已提交的行被修改或删除 | 拒绝提交 |
| 暂存了某个变更 `affected_paths` 内的代码，而该变更还没开工 | 警告；`enforce: strict` 时拒绝 |
| 暂存了已开工变更的代码，但它的 `events.jsonl` 没有暂存或不是最新 | 警告，提示 `git add .devflow/changes/<id>` |
| 有已开工的变更时，暂存了不属于任何进行中变更、也不在 `.devflow/` 下的文件 | 警告，列出这些文件 |
| 知识页有问题（过期、引用失效等） | 警告 |

规范、事件日志、批准快照和证据附件，按暂存区的内容检查。方案格式和业务状态仍然按工作树计算，所以用 `git add -p` 部分暂存时，请核对相关文件是否都暂存了。

紧急情况可以用 `git commit --no-verify` 跳过本地门禁，CI 中的检查仍然有效。

## 安全模型

DevFlow 防的是 Agent 的**失误和越级**：跳过审批、自己判定通过、手改规范。它**不防恶意篡改**，有写权限的 Agent 理论上能改任何文件。防线有三层：

1. **人专属命令要求交互终端**：`approve`、`archive`、`evidence confirm` 在非交互终端中直接拒绝。在 Codex 下，这一层可以被绕过（见[选择你的 Agent](#选择你的-agent)）。
2. **Agent 侧的禁止规则**：Claude Code 用 `.claude/settings.json` 禁止运行 approve 和 archive，并禁止直接编辑 `.devflow/specs/` 和 `events.jsonl`；Codex 用 `.codex/rules/devflow.rules`。
3. **git 门禁和代码审查**：批准记录随 `events.jsonl` 进入提交，审查代码时能看到谁在什么时候批准了什么。

另外：

- `verify` 只运行 `project.yaml` 中的命令，而 `project.yaml` 计入批准哈希。
- 审查页离线生成，不加载任何外部资源，也不执行方案里的 HTML 或脚本。
- 知识页和证据都不能引用 `exclude` 中的文件。

## 常见问题与排错

**提交后状态从 `ready_to_archive` 变回了 `applying`**
提交本身不会造成这种情况。原因是验证之后有文件被改过，包括文档。运行 `devflow resume <id>` 查看原因，然后重新 `verify` 并补齐证据。

**状态是 `rebase_required`**
批准之后，有提交改动了 `affected_paths` 中的文件，或者同一能力的规范被别的变更改了。让 Agent 检查方案是否仍然适用，必要时修改，然后重新批准。

**archive 被拒："规范 X 在本变更批准后被修改过"**
另一个修改同一能力的变更先归档了。让 Agent 根据最新规范更新本变更的规范增量，然后重新批准、重新验证。

**archive 被拒："知识页有 N 个错误"**
运行 `devflow wiki lint` 查看，或者让 Agent 用 devflow-scan 修复。

**提交被拒："内容与 specs.lock 不符"**
有人手改了 `.devflow/specs/`。用 `git restore <文件>` 撤销，新加的文件直接删除。要改规范，请新建一个变更并归档。

**提交被拒："事件日志的已提交内容被修改或删除"**
用 `git restore .devflow/changes/<id>/events.jsonl` 恢复。

**`.DS_Store` 或编辑器临时文件让批准失效、提交被拒**
devflow 只看 git 会跟踪的文件。出现这类问题，说明这些临时文件没有被忽略。把它们加进 `.gitignore`：

```bash
echo '.DS_Store' >> .gitignore
```

**render 报"审查页内容有 N 处不允许的写法"**
错误信息里有文件名和行号。把 `html`、`svg` 代码块改成 `flow` 等图形块，去掉代码块属性和图片。

**知识页报 `verified_commit ... 必须是提交哈希`**
给哈希加上引号：`verified_commit: "1234567"`。

**Codex 没有拦截 `devflow approve`**
第一次在项目中使用 Codex 时，要选择信任该项目，`.codex/rules/` 才会加载。即使加载了规则，交互终端检查在 Codex 下仍可能被绕过。

## 升级 devflow

1. 重新打包，并全局安装新版本。
2. 在每个已启用 DevFlow 的项目里运行 `devflow update`，重新生成技能和说明段落。手工改过的技能文件会被覆盖。
3. 运行 `devflow doctor`，确认 hook 和 Agent 文件都是最新的。

## 已知限制

- **规范从变更中逐步积累**：`.devflow/specs/` 一开始是空的，只随着归档增长。DevFlow 不会从现有代码自动生成规范，因为那样的规范没有经过审核。
- **没有图形界面**：审查靠离线 HTML 页面，批准和归档靠终端命令。
- **不自动提交、推送或部署**：这些都由人决定。
