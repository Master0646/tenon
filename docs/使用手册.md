## 1. DevFlow 是什么

DevFlow 是嵌入 AI 编码 Agent（Claude Code、Codex）使用的软件工程流程。它让 Agent 改代码之前先出方案，由人审批，再实现、验证、归档。需求、行为规范、设计原因都以文件形式留在仓库的 `.devflow/` 里，换一个会话、换一个 Agent 都能接着做。

DevFlow 自己**不调用任何模型**。三方分工：

| 谁 | 负责 |
| --- | --- |
| **人** | 审查方案、批准（`devflow approve`）、提交代码、归档（`devflow archive`）、维护验证命令 |
| **Agent** | 读代码、写方案、写代码与测试、更新知识页、带引用回答问题——通过 DevFlow 技能完成 |
| **devflow 命令** | 只做确定性的事：校验格式、绑定批准哈希、判定状态、运行验证命令、合并规范、渲染审查页、提交时把关 |

一句话流程：

```text
提方案(Agent) → 审查并批准(人) → 实现并验证(Agent) → 提交(人) → 更新知识页(Agent) → 归档(人)
```

## 2. 安装与升级

### 2.1 要求

- Node 22 或更高版本
- git
- 至少一个 Agent：Claude Code 或 Codex

### 2.2 从源码打包并全局安装（第一步）

先做这一步。不全局安装，终端里没有 `devflow` 命令，pre-commit hook 也无法运行。

```bash
cd devflow && npm install && npm pack
```

```bash
npm install -g ./devflow-0.1.0.tgz
```

```bash
devflow --version
```

输出 `0.1.0` 即安装成功。打包生成的 `devflow-0.1.0.tgz` 已被 `.gitignore` 忽略，安装后可以删除。

### 2.3 开发模式（不打包）

在 devflow 仓库里直接运行源码，需要 Node 23.6 或更高版本：

```bash
node src/cli.ts help
```

本手册的命令都写作 `devflow <命令>`；开发模式下换成 `node <devflow 目录>/src/cli.ts <命令>`。

### 2.4 升级

1. 重新打包并安装新版本。
2. 在每个已启用 DevFlow 的项目里运行 `devflow update`，重新生成技能与说明文件。
3. 运行 `devflow doctor` 确认 hook 和 Agent 文件都是最新的。

> 如果 devflow 的安装位置变了，pre-commit hook 会指向旧路径。`devflow doctor` 会报错并提示运行 `devflow init` 重新安装 hook（`init` 不会覆盖已有文件）。

## 3. 核心概念

| 概念 | 位置 | 说明 |
| --- | --- | --- |
| **变更（change）** | `.devflow/changes/<id>/` | 一次需求的方案：提案、规范增量、设计、任务。审批、开工、验证、归档都以变更为单位 |
| **规范（spec）** | `.devflow/specs/<能力>/spec.md` | 已批准的系统行为契约（"必须怎样"）。只能通过归档变更来修改 |
| **规范增量（delta spec）** | `changes/<id>/specs/<能力>/spec.md` | 本次变更对规范的增、改、删 |
| **知识页（knowledge）** | `.devflow/knowledge/pages/*.md` | 代码"现在是怎样"的说明，每条事实带源码出处 |
| **事件日志** | `changes/<id>/events.jsonl` | 批准、开工、任务完成、验证、归档的记录。只能由 devflow 命令追加 |
| **派生状态** | 不存储 | 每次由变更文件、事件日志和 git 现算（见第 6 节） |
| **批准哈希** | 记录在事件日志 | 批准时对被审文件计算的哈希。被审文件一改，批准自动失效 |
| **验证命令** | `.devflow/project.yaml` | 由人维护。`devflow verify` 只运行这里声明的命令 |

**被审文件**是变更目录下除 `events.jsonl` 之外的所有文件，再加上 `.devflow/project.yaml`。把 `project.yaml` 计入，是为了防止批准之后有人改弱验证命令。

## 4. 在项目里启用 DevFlow

以下操作在**已有至少一次提交**的 Git 项目根目录进行。开始前确认已按 [2.2](#22-从源码打包并全局安装第一步) 全局安装，`devflow --version` 有输出。

### 4.1 初始化

```bash
devflow init
```

不带 `--agents` 时，只为项目里检测到的 Agent 生成文件：有 `.claude/` 或 `CLAUDE.md` 就装 Claude Code，有 `.codex/`、`.agents/` 或 `AGENTS.md` 就装 Codex；一个都检测不到时两个都装，并给出提示。要指定，写 `--agents claude`、`--agents codex` 或 `--agents claude,codex`。生成的内容：

| 文件 | 作用 |
| --- | --- |
| `.devflow/` | 规范、变更、知识页的目录与 `project.yaml` |
| `.git/hooks/pre-commit` | 提交时运行 `devflow check --staged`。已有别的 hook 时不覆盖，会提示你手动加一行 |
| `.gitignore` | 追加 `.devflow/runtime/`（验证日志、审查页等本地文件） |
| `.claude/skills/devflow-*/`、`CLAUDE.md` | Claude Code 的技能与说明 |
| `.claude/settings.json` | Claude Code 的禁止规则（合并进已有设置，不覆盖） |
| `.agents/skills/devflow-*/`、`AGENTS.md` | Codex 的技能与说明 |
| `.codex/rules/devflow.rules` | Codex 的禁止规则 |

`CLAUDE.md` 与 `AGENTS.md` 中由 DevFlow 维护的内容放在 `<!-- devflow:begin -->` 与 `<!-- devflow:end -->` 之间。这两行之外的内容不会被改动。

### 4.2 声明验证命令（人来做）

编辑 `.devflow/project.yaml`：

```yaml
verify:
  - name: backend-test
    run: mvn -q -B test
    cwd: backend
  - name: frontend-build
    run: npm run build
    cwd: frontend
```

不声明验证命令时，`devflow verify` 的结果永远是 `unknown`，变更无法归档。

**为什么要配**：`verify` 是"实现完成"的唯一客观判据。Agent 说做完了不算，这里的命令全部退出码为 0 才算。验证通过后，状态才会变成 `ready_to_archive`。

**为什么由人维护**：`project.yaml` 计入每次批准的哈希。如果 Agent 能改它，就能把验证改弱（例如删掉测试）让自己通过。所以只有人改它，改了之后已有的批准会失效。

**怎么配**：写你平时在本地确认"没改坏"时会跑的命令，通常是测试，加上编译或构建。每条命令可选 `cwd`（相对项目根目录）。常见技术栈：

| 技术栈 | `run` | 说明 |
| --- | --- | --- |
| Maven | `mvn -q -B test` | `-B` 关闭交互输出 |
| Gradle | `./gradlew test --console=plain` | |
| Node（npm） | `npm test`、`npm run build` | 前端没有测试时至少配构建 |
| Python | `pytest -q` | |
| Go | `go test ./...` | |

项目没有测试时，验证只能证明能编译。可以在第一个变更里让 Agent 补测试依赖和测试。

### 4.3 忽略构建产物

验证命令生成的文件（如 `target/`、`dist/`、`node_modules/`）必须写进 `.gitignore`。否则验证期间工作树会发生变化，结果会被判为 `unknown`。

### 4.4 自检

```bash
devflow doctor
```

每一项显示 `✓`（正常）、`!`（警告）或 `✗`（错误），问题后面附修复命令。有 `✗` 时退出码为 1。

### 4.5 生成知识页（可选）

在 Agent 里说：

> 使用 devflow-scan 技能，为本项目生成知识页。

Agent 会按业务模块写 `.devflow/knowledge/pages/*.md`，并运行 `devflow wiki lint` 直到没有错误。小项目可以跳过这一步，原因见[第 13 节](#13-已知限制与使用建议)。

### 4.6 提交

```bash
git add -A && git commit -m "启用 DevFlow"
```

> 使用 Codex 时，第一次在项目里打开 Codex 要选择**信任**该项目，`.codex/rules/` 才会加载。

## 5. 走一遍完整的变更

下面以"禁用用户接口只允许 ADMIN 调用"为例。

### 第 1 步：提方案（Agent）

在 Agent 里说：

> 使用 devflow-propose 技能，为下面的需求提出变更方案：禁用用户接口只允许 ADMIN 角色调用；前端对非 ADMIN 用户隐藏禁用按钮。

Agent 会：

1. 信息不足时先问你；
2. 读相关代码和当前规范；
3. 运行 `devflow new 2026-11-06-admin-only-disable` 生成目录；
4. 写 `change.yaml`、`proposal.md`、规范增量、`design.md`、`tasks.yaml`；
5. 运行 `devflow validate`，直到没有错误；
6. 运行 `devflow render`，告诉你审查页路径和内容哈希。

Agent 在这一步**不会改业务代码**。

### 第 2 步：审查（人）

用浏览器打开 `.devflow/runtime/rendered/<id>.html`。审查页由被审文件直接生成，不经过模型改写，包含：

| 面板 | 内容 |
| --- | --- |
| A 提案 | 为什么、改什么、影响、不做什么 |
| B 规范增量 | 新增（绿）、修改（黄）、删除（红）的需求 |
| C 设计 | 技术方案与流程图 |
| D 任务与依赖 | 任务表与自动生成的依赖图 |
| E 被审文件与内容哈希 | 每个文件的哈希与总哈希 |

重点看三处：验收条件是否真能验证、`affected_paths` 是否覆盖要改的代码、"不做什么"是否符合预期。

**要修改时**：直接告诉 Agent 改哪里。Agent 改完会重新校验、重新生成审查页，哈希随之变化。

### 第 3 步：批准（人，在自己的终端）

```bash
devflow approve 2026-11-06-admin-only-disable
```

终端会显示基线提交、批准人、内容哈希和被审文件清单。**核对哈希与审查页一致**，然后在提示处输入 `y` 回车：

```text
确认批准？输入 y 确认：y
✓ 已批准 2026-11-06-admin-only-disable
```

只有看到 `✓ 已批准` 才算成功。输入其他内容、直接回车或按 Ctrl+D，都会显示"已取消"，状态仍为 `draft`。

> 批准人取自 `git config user.name`，未配置时无法批准。

### 第 4 步：实现与验证（Agent）

在 Agent 里说：

> 使用 devflow-apply 技能实现变更 2026-11-06-admin-only-disable。

Agent 会：

1. 运行 `devflow apply <id> --start` 记录开工；
2. 按依赖顺序实现任务，每完成一个就写测试、运行，然后运行 `devflow task done <id> <任务ID>`；
3. 全部完成后运行 `devflow verify <id>`，失败就修复后重跑，直到通过：

```text
✓ backend-test  退出码 0  10.3s
结果：pass；状态：ready_to_archive
```

Agent 发现方案本身有问题时，会停下来告诉你，而不是自行修改方案。修改方案会让批准失效，需要你重新批准。

### 第 5 步：提交代码（人）

由你决定何时提交、提交信息怎么写。DevFlow 不会自动提交或推送。

提交代码时，把变更目录 `.devflow/changes/<id>/` 一起提交：其中的 `events.jsonl` 是批准与验证记录。

> 提交本身不影响验证结果：判定依据是文件内容，不是 git 状态。但如果验证之后又改了任何文件（包括文档），状态会回到 `applying`，需要重新运行 `devflow verify`。所以任务文档、说明文档要在 verify 之前写完。

### 第 6 步：归档准备（Agent）

在 Agent 里说：

> 使用 devflow-archive 技能为变更 2026-11-06-admin-only-disable 做归档准备。

Agent 会更新相关知识页，在页面里链接到归档后的设计文档（例如 `../../changes/archive/2026-11-06-admin-only-disable/design.md`），并确认 `devflow wiki lint` 没有错误。项目里没有知识页时，这一步可以跳过。

### 第 7 步：归档（人，在自己的终端）

```bash
devflow archive 2026-11-06-admin-only-disable
```

终端会列出将写入的规范文件和将移动的目录。确认后输入 `y`：

```text
✓ 已归档到 .devflow/changes/archive/2026-11-06-admin-only-disable；更新规范：.devflow/specs/user-management/spec.md
```

然后提交归档结果。一个功能因此分成两次提交，这是有意的：知识页的 `verified_commit` 要指向包含代码改动的提交，所以代码必须先提交。推荐顺序：

1. 第 5 步：提交代码，连同变更目录（含 `events.jsonl` 批准记录）一起提交；
2. 第 6 步：Agent 更新知识页；
3. 第 7 步：`devflow archive`；
4. 提交知识页、规范、`specs.lock` 和归档目录：

```bash
git add -A && git commit -m "归档 2026-11-06-admin-only-disable"
```

### 第 8 步：以后

任何新会话都可以问：

> 禁用用户为什么要求操作者是 ADMIN？是哪次变更引入的？

Agent 会从 `.devflow/changes/archive/` 和 `.devflow/specs/` 里找到需求、规范和设计原因，并给出出处。

## 6. 状态与下一步

运行 `devflow status` 查看所有进行中的变更，`devflow status <id>` 查看一个，`devflow status --all` 同时列出已归档的变更和归档时间。状态不存储，每次现算。

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `draft` | 尚未批准，或批准后被审文件改过 | Agent 写完方案后，人审查并 `approve` |
| `rebase_required` | 已批准、未开工，但批准后有提交改动了 `affected_paths` | 人重新评估方案（必要时让 Agent 修改），再 `approve` |
| `approved` | 已批准，可以开工 | Agent 用 devflow-apply 实现 |
| `applying` | 已开工，未验证、任务未完成，或验证后代码有改动 | Agent 继续实现，或重新 `verify` |
| `needs_fix` | 最近一次验证结果为 `fail` 或 `unknown` | 看验证日志修复，或处理"无法运行"的原因后重新 `verify` |
| `ready_to_archive` | 任务全部完成，且验证通过的就是当前代码 | 人提交代码 → Agent 归档准备 → 人 `archive` |
| `archived` | 已归档 | — |

几条规则：

- **改方案 = 重新批准**：批准后改动任何被审文件或 `project.yaml`，状态回到 `draft`。
- **重新批准 = 重新开工**：重新批准之后，之前的开工和验证记录不再算数。
- **验证绑定代码**：验证结果绑定当时的工作树内容（不含 `.devflow/`）。之后改了任何文件，都要重新验证。
- **unknown 不是通过**：验证命令无法运行、超时（30 分钟）、没有声明命令、验证期间工作树发生变化，结果都是 `unknown`。

## 7. 命令参考

所有命令都支持 `--json`，输出机器可读结果。出错时退出码为 1，并在 `✗` 后给出原因与修复提示。

### 初始化与维护

| 命令 | 说明 |
| --- | --- |
| `devflow init [--agents claude,codex]` | 创建 `.devflow/`、安装 hook、生成 Agent 文件（默认只装检测到的 Agent）。可以重复运行，不覆盖已有文件 |
| `devflow update [--agents …]` | 重新生成 Agent 文件。不写 `--agents` 时，更新已安装过的那些 |
| `devflow doctor` | 自检。在 Git 仓库之外运行时只检查环境 |
| `devflow --version` | 显示版本号 |

### 方案阶段

| 命令 | 说明 |
| --- | --- |
| `devflow new <id>` | 生成变更目录骨架。id 用小写字母、数字、连字符，建议 `<日期>-<英文短名>` |
| `devflow validate <id>` | 校验文件是否齐全、格式是否正确，并对当前规范做一次合并试算；同时报出审查页会拒绝的写法（含图语法错误），定位到源文件行号。validate 通过，render 就不会因写法失败 |
| `devflow render <id> [-o 文件]` | 生成离线审查页，默认在 `.devflow/runtime/rendered/<id>.html` |
| `devflow approve <id>` | **人专属**。显示哈希，确认后记录批准 |

### 实现阶段

| 命令 | 说明 |
| --- | --- |
| `devflow apply <id> --start` | 记录开工。只能从 `approved` 开始 |
| `devflow task done <id> <任务ID>` | 记录任务完成。依赖的任务必须先完成 |
| `devflow verify <id>` | 运行 `project.yaml` 中的命令。全部通过时退出码为 0；日志在 `.devflow/runtime/verify/<id>/` |

### 收尾阶段

| 命令 | 说明 |
| --- | --- |
| `devflow archive <id>` | **人专属**。合并规范增量、更新 `specs.lock`、移动变更目录。中断后重新运行即可继续 |

### 查看与检查

| 命令 | 说明 |
| --- | --- |
| `devflow status [id] [--all]` | 状态、任务进度、原因；`--all` 同时列出已归档的变更 |
| `devflow wiki lint` | 知识页校验（见 8.8） |
| `devflow check [--staged]` | 门禁检查（见第 10 节） |

## 8. 文件格式参考

所有 YAML 文件都以 `schema_version: 1` 开头。格式写错时，`devflow validate` 会给出文件、行号和正确示例。

### 8.1 project.yaml（人维护）

```yaml
schema_version: 1
verify:                 # devflow verify 只运行这里的命令
  - name: backend-test  # 名称，不可重复
    run: mvn -q -B test # 用 sh -c 执行
    cwd: backend        # 可选，相对仓库根目录
exclude:                # 知识页不得引用的文件（规则同 .gitignore）
  - ".env*"
  - "**/*.pem"
enforce: warn           # warn | strict，见第 10 节
```

### 8.2 change.yaml

```yaml
schema_version: 1
title: 禁用用户需要 ADMIN 角色
affected_paths:         # 本变更会改动的代码（glob），不能写 .devflow/ 下的路径
  - backend/src/main/java/com/example/admin/user/**
  - frontend/src/views/UserList.vue
```

`affected_paths` 有两个用途：批准后若有提交改动这些路径，状态变为 `rebase_required`；提交未开工变更的这些文件时，门禁会警告。

### 8.3 proposal.md

建议包含四节：`## 为什么`、`## 改什么`、`## 影响`、`## 不做什么`。不能只有标题没有正文。

### 8.4 规范增量 specs/<能力>/spec.md

```markdown
## ADDED Requirements

### Requirement: 禁用用户需要 ADMIN 角色
系统 SHALL 拒绝非 ADMIN 用户调用禁用接口。

#### Scenario: 普通用户禁用他人
- WHEN USER 角色调用 POST /api/users/{id}/disable
- THEN 返回 403，用户状态不变

## MODIFIED Requirements
### Requirement: <当前规范中已有的名称>
（整条需求的新全文）

## REMOVED Requirements
### Requirement: <当前规范中已有的名称>
**Reason**: 删除原因
```

规则：

- 能力名（目录名）用小写字母、数字、连字符。
- 每条新增或修改的需求必须有 `SHALL` / `MUST`（或"必须"），且至少有一个 `#### Scenario:`。
- 新能力只能 ADDED，可以加 `## Purpose` 说明这个能力是什么。
- MODIFIED / REMOVED 的名称必须与当前规范完全一致。
- 不改变对外行为的变更（如纯重构）可以不写规范增量；validate 会给出提醒，不算错误。

### 8.5 design.md 与审查页的写法限制

流程图使用代码块：

````markdown
```flow TB
(开始) -> {操作者是 ADMIN?}
{操作者是 ADMIN?} -> 抛出 403: 否
{操作者是 ADMIN?} -> 原有校验: 是
```
````

- `A -> B: 标签`：冒号后面是连线上的标签；`{条件?}` 是判断节点；`(开始)` 是起止节点。
- 可用的图：`flow`、`sequence`、`tree`、`er`。
- 普通代码块只写语言名，例如 ` ```java `。

审查页会**拒绝**以下写法（`devflow render` 报错并给出行号）：`html` / `svg` 代码块、带属性的代码块（如 ` ```ts src=… `）、`:::` 块、图片。正文中的 `<` `>` 会被转义，按原样显示。

### 8.6 tasks.yaml

```yaml
schema_version: 1
tasks:
  - id: T1
    title: UserService#disable 增加操作者角色校验
    acceptance:
      - USER 角色调用返回 403
  - id: T2
    title: 前端对非 ADMIN 隐藏禁用按钮
    depends_on: [T1]
```

- 任务 id 以字母开头，不能重复；`depends_on` 引用的任务必须存在，依赖不能成环。
- **不能写进度字段**（`status`、`done`）。进度由 `devflow task done` 记在事件日志里，否则勾选一次任务就会让批准失效。

### 8.7 events.jsonl

每行一个事件，类型为 `approved`、`apply-started`、`task-done`、`verified`、`archived`。**只能由 devflow 命令追加**；已提交的行被改动或删除时，提交会被门禁拒绝。

### 8.8 知识页 knowledge/pages/<slug>.md

```markdown
---
schema_version: 1
title: 用户管理
verified_commit: "9f3a2c1"
sources:
  - path: backend/src/main/java/com/example/admin/user/UserController.java
    symbol: UserController#list
  - path: backend/src/main/resources/mapper/UserMapper.xml
    lines: [10, 30]
related_specs: []
---

# 用户管理
……
```

- `verified_commit` **要加引号**：形如 `1234567` 的短哈希不加引号时，会被 YAML 当成数字读取。
- `symbol` 写成 `类名` 或 `类名#方法名`，必须与源码文字一致。
- 正文里用完整路径引用的文件，也要列进 `sources`；漏列的文件改了，本页不会被标为过期。
- 每个页面都要在 `knowledge/index.md` 里有一行：`- [标题](pages/<slug>.md) — 摘要`。

`devflow wiki lint` 的检查项：

| 问题 | 级别 |
| --- | --- |
| frontmatter 缺失或字段不合法 | 错误 |
| 引用的文件不存在、符号找不到、行号越界 | 错误 |
| 引用了 `exclude` 中的文件 | 错误 |
| `index.md` 漏列页面或列了不存在的页面 | 错误 |
| 正文链接指向不存在的页面或文件（指向进行中变更的归档位置除外） | 错误 |
| 引用的文件在 `verified_commit` 之后有改动（stale） | 警告 |
| 正文引用了未列入 `sources` 的文件 | 警告 |
| 没有任何知识页（`doctor` 也会提示；提交门禁不提示） | 警告 |

## 9. Agent 技能

`devflow init` 为每个 Agent 安装五个技能。Claude Code 中可以直接说技能名，Codex 中用 `$技能名` 调用。

| 技能 | 什么时候用 | 典型说法 |
| --- | --- | --- |
| `devflow-propose` | 新功能、行为修改、修复，先出方案 | "用 devflow-propose 提一个变更：……" |
| `devflow-apply` | 实现已批准的变更并验证 | "用 devflow-apply 实现变更 <id>" |
| `devflow-archive` | 验证通过后，归档前更新知识页 | "用 devflow-archive 为变更 <id> 做归档准备" |
| `devflow-scan` | 生成或修复知识页 | "用 devflow-scan 生成知识页" |
| `devflow-ask` | 带出处回答项目问题 | "X 在哪里实现？"（不说技能名也会用到） |

`CLAUDE.md` / `AGENTS.md` 中的 DevFlow 段落会提醒 Agent：改代码前先出方案、关于项目的事实要带出处、不运行 approve 和 archive。

## 10. 提交门禁

pre-commit hook 运行 `devflow check --staged`。CI 中可以运行 `devflow check`。

| 规则 | 结果 |
| --- | --- |
| `.devflow/` 下的文件格式错误 | 拒绝提交 |
| `.devflow/specs/` 的内容与 `specs.lock` 不符（手改、手加、手删） | 拒绝提交 |
| `events.jsonl` 中已提交的行被修改或删除 | 拒绝提交 |
| 暂存了某变更 `affected_paths` 内的代码，而该变更还没开工 | 警告；`enforce: strict` 时拒绝 |
| 知识页问题（过期、引用失效等） | 警告 |

紧急情况可以用 `git commit --no-verify` 跳过本地门禁，CI 中的检查仍会生效。

## 11. 安全模型

DevFlow 防的是 Agent 的**失误与越级**（跳过审批、自己判定通过、手改规范），**不防恶意篡改**：有写权限的 Agent 理论上能改任何文件。防线有三层：

1. **人专属命令需要交互终端**：`approve` 和 `archive` 在非交互终端中直接拒绝。
   - Claude Code 的命令不在交互终端中运行，此防线有效。
   - Codex 可以由模型选择分配交互终端，此防线在 Codex 下**可被绕过**。
2. **Agent 侧禁止规则**：
   - Claude Code：`.claude/settings.json` 禁止运行 `devflow approve` / `archive`，禁止直接编辑 `.devflow/specs/` 和 `events.jsonl`。已实测拦截。
   - Codex：`.codex/rules/devflow.rules` 禁止这两个命令。只在项目被信任时加载，属于实验性功能。
3. **git 门禁与代码审查**：见第 10 节。批准记录随 `events.jsonl` 进入提交，审查代码时能看到谁在何时批准了什么。

另外：

- `verify` 只运行 `project.yaml` 中的命令；`project.yaml` 计入批准哈希，批准后改动它会让批准失效。
- 审查页离线生成，不加载任何外部资源，不执行方案中的 HTML 或脚本。
- 知识页不得引用 `exclude` 中的文件（默认包含 `.env*`、`*.pem`、`*.key`、`node_modules`）。

## 12. 常见问题与排错

**运行了 `devflow approve`，状态还是 `draft`**
确认提示处必须输入 `y` 并回车，看到 `✓ 已批准` 才算成功。显示"✗ 未批准"或没有输出，都表示没有批准。用 `devflow status <id>` 确认。

**提示"approve 只能由人在交互终端中运行"**
命令是在非交互环境中运行的，例如被 Agent 代为执行、在某些编辑器的任务面板里、或通过管道运行。请在普通终端窗口中运行。

**提示"未配置 git user.name"**
```bash
git config user.name "你的名字"
```

**状态是 `rebase_required`**
批准后，有提交改动了 `affected_paths` 中的文件，方案可能需要调整。让 Agent 检查方案是否仍然适用，必要时修改，然后重新 `approve`。

**提交后状态从 `ready_to_archive` 变回 `applying`**
提交本身不会导致这种情况。原因是验证之后有文件被改过，包括文档。运行 `devflow status <id>`，原因会显示为"验证后代码有改动"；重新运行 `devflow verify <id>` 即可。

**verify 结果是 `unknown`**
| 提示 | 处理 |
| --- | --- |
| 没有声明任何验证命令 | 在 `project.yaml` 中加入 `verify`（会让批准失效，需重新批准） |
| 命令无法运行 | 命令不存在或不可执行，例如没装 `mvn`。安装后重新验证 |
| 超时 | 单个命令超过 30 分钟 |
| 验证期间工作树发生变化 | 构建产物没有被 `.gitignore` 忽略，补上后重新验证 |

**archive 被拒："规范 X 在本变更批准后被修改过"**
另一个修改同一能力的变更先归档了。让 Agent 根据最新规范更新本变更的规范增量，然后重新批准、重新验证。

**archive 被拒："知识页有 N 个错误"**
运行 `devflow wiki lint` 查看，或让 Agent 用 devflow-scan 修复。

**archive 中途被打断**
再运行一次 `devflow archive <id>`。它会发现未完成的事务，从中断处继续，不会重复写入。

**提交被拒："内容与 specs.lock 不符"**
有人手改了 `.devflow/specs/`。用 `git restore <文件>` 撤销（新加的文件直接删除）。要改规范，请新建变更并归档。

**`.DS_Store`、编辑器临时文件让批准失效或提交被拒**
devflow 在 `.devflow/` 里只看 git 会跟踪的文件：被 `.gitignore`（包括全局忽略规则）忽略的文件，不参与校验、批准哈希和门禁。出现这类问题，说明这些临时文件没有被忽略。把它们加进项目的 `.gitignore`，例如：
```bash
echo '.DS_Store' >> .gitignore
```

**提交被拒："事件日志的已提交内容被修改或删除"**
用 `git restore .devflow/changes/<id>/events.jsonl` 恢复。

**doctor 报"hook 指向的文件不存在"**
devflow 的安装位置变了。运行 `devflow init` 重新安装 hook。

**doctor 报"Agent 文件与当前版本不一致"**
运行 `devflow update`。技能文件和说明段落由 devflow 生成，手工修改会在 update 时被覆盖。

**render 报"审查页内容有 N 处不允许的写法"**
错误信息中有文件和行号。把 `html` / `svg` 块改成 `flow` 等图形块；去掉代码块属性和图片。

**知识页报 `verified_commit ... 必须是提交哈希`**
给哈希加引号：`verified_commit: "1234567"`。

**Codex 没有拦截 `devflow approve`**
第一次在项目中使用 Codex 时需要选择信任该项目，`.codex/rules/` 才会加载。另见第 11 节：在 Codex 下，交互终端检查可能被绕过。

## 13. 已知限制与使用建议

- **知识页在小项目上作用有限**：在一个 25 个文件的演示项目上评测，有无知识页，回答准确率相同，有知识页时每题还多用约 25% 的轮数。知识页的价值在于代码里看不出来的东西，例如设计原因、历史变更，以及 Agent 读不完代码的大项目。小项目可以不做 scan，只靠归档积累设计原因。
- **规范从变更中逐步积累**：`.devflow/specs/` 一开始是空的，只通过归档变更增长。DevFlow 不会从现有代码自动生成规范，因为那样的规范没有经过审核。
- **文档最好在 verify 之前写完**：verify 之后改任何文件都需要重新验证。
- **门禁检查的是工作树内容**：用 `git add -p` 部分暂存时，`check --staged` 可能误拦或漏过。
- **没有图形界面**：审查靠离线 HTML 页面，批准与归档靠终端命令。
- **不自动提交、推送、部署**：这些都由人决定。
