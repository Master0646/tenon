DevFlow 使用手册

让 AI 编码 Agent 先出方案、经你批准再改代码，并把需求和设计原因留在仓库里。

适用版本：devflow 0.2.0　·　更新：2026-11-08　·　本手册的输出示例均来自 0.2.0 实测；approve、archive、evidence confirm 只能由人运行，它们的输出按源码 src/cli.ts 核对。

DevFlow 嵌入你已有的 Agent（Claude Code 或 Codex）使用，自己不调用任何模型。Agent 负责读代码、写方案、写代码；devflow 命令只做确定性的事：校验格式、给批准绑定哈希、计算状态、运行验证命令、合并规范、在提交时把关。

只负责审查和批准？ 先看一页概览，再读快速入门的第 1 步，以及第 2 步：审查、第 3 步：批准和第 8 步：归档。其余工作由 Agent 完成。

一句话流程

输出
提方案(Agent) → 审查并批准(人) → 实现、验证、记证据(Agent) → 提交代码(人) → 更新知识页(Agent) → 归档(人)

选择你的 Agent

两种 Agent 用法相同。区别有两点：怎样调用技能，以及安全防线有多强。

Claude CodeCodex
调用技能直接说技能名："用 devflow-propose 提一个变更"用 $devflow-propose
生成的文件.claude/skills/devflow-*/、CLAUDE.md、.claude/settings.json.agents/skills/devflow-*/、AGENTS.md、.codex/rules/devflow.rules
禁止 Agent 运行 approve / archive有效（已实测拦截）实验性：项目被信任后才加载规则
交互终端防线有效：Agent 的 shell 不是交互终端可被绕过：模型可以自行申请交互终端

两个都用也可以，devflow init 会为两者都生成文件。

快速入门

做完这一节，你会有一个启用了 DevFlow、提交门禁生效、能跑验证命令的项目。用时约 5 分钟。

前提：Node 22 或更高版本，git，以及一个至少已有一次提交的 Git 项目。

1. 安装 devflow

在 devflow 源码目录里打包，然后全局安装：

终端
npm install && npm pack
终端
npm install -g ./devflow-0.2.0.tgz
终端
devflow --version

预期输出：

输出
0.2.0

必须全局安装：终端里要能运行 devflow，pre-commit hook 也依赖这个命令。

开发 devflow 本身时，可以不打包，直接运行 node src/cli.ts <命令>（需要 Node 23.6 或更高版本）。

2. 在项目里初始化

在你的项目根目录运行：

终端
devflow init

预期输出（节选）：

输出
+ .devflow/project.yaml
+ .devflow/specs/specs.lock
+ .devflow/knowledge/index.md
+ .gitignore（追加 .devflow/runtime/）
✓ pre-commit hook 已安装：/path/to/project/.git/hooks/pre-commit
✓ .claude/skills/devflow-propose/SKILL.md
✓ CLAUDE.md
✓ .claude/settings.json
…

init 只为检测到的 Agent 生成文件：项目里有 .claude/ 或 CLAUDE.md，就装 Claude Code；有 .codex/、.agents/ 或 AGENTS.md，就装 Codex。两种都没检测到时，两个都装。要指定，写 --agents claude、--agents codex 或 --agents claude,codex。

init 可以重复运行，不会覆盖已有文件。CLAUDE.md 和 AGENTS.md 里，只有 <!-- devflow:begin --> 和 <!-- devflow:end --> 之间的内容由 DevFlow 维护，其余内容不会被改动。

注意

项目里已经有别的 pre-commit hook 时，init 不会覆盖它，而是提示你手动加一行。

代码在别的仓库时：有些项目把 devflow 放在一个工作区仓库里，代码放在旁边几个兄弟仓库。在 .devflow/project.yaml 里声明它们（路径相对本仓库根，每项是一个 Git 仓库的根）：

YAML
code_roots: ["../backend", "../frontend"]

然后再运行一次 devflow init，它会给每个代码仓库也装上 pre-commit hook：

输出
✓ 代码仓库 pre-commit hook 已安装：/path/to/backend/.git/hooks/pre-commit

声明之后：

  • 代码哈希只算这些仓库：它们的改动让验证和证据过期，本仓库里的文档改动不会。
  • affected_paths 写成以该项开头的路径，例如 ../backend/src/main/**；没声明的 .. 路径会被 validate 拒绝。
  • 批准后代码仓库里有提交改动了这些路径，变更进入 rebase_required。
  • 在代码仓库里提交未开工变更的代码时，hook 按 enforce 警告或拒绝。
  • 证据的 test 和附件可以是代码仓库里的文件。

3. 声明验证命令人来做

编辑 .devflow/project.yaml，把 verify: [] 换成你平时用来确认"没改坏"的命令：

YAML
verify:
  - name: unit-tests     # 名称，不能重复；任务的验收条件会用这个名字引用它
    run: npm test        # 用 sh -c 执行
  - name: backend-test
    run: mvn -q -B test
    cwd: backend         # 可选，相对项目根目录
注意

只有这里声明的命令会被 devflow verify 运行，所有命令退出码为 0 才算通过。这个文件由人维护，并计入每次批准的哈希：如果 Agent 能改它，就能删掉测试让自己通过。所以批准之后改动它，已有的批准会失效。

常见技术栈：

技术栈run
Nodenpm test；前端没有测试时，至少配 npm run build
Mavenmvn -q -B test（-B 关闭交互输出）
Gradle./gradlew test --console=plain
Pythonpytest -q
Gogo test ./...

验证命令生成的文件（dist/、target/、node_modules/ 等）必须写进 .gitignore。否则验证期间工作树发生变化，结果会被记为 unknown。

4. 验证你的安装

终端
devflow doctor

预期输出：

输出
✓ Node：v26.13.0
✓ git：git version 2.39.5
✓ 仓库：/path/to/project
✓ 初始化：.devflow/ 存在
✓ hook：指向 /opt/homebrew/lib/node_modules/devflow/dist/cli.js
✓ Agent 文件（claude）：与当前版本一致
! 知识页：知识页为空，devflow-archive 没有页面可更新
    修复：用 devflow-scan 技能生成知识页；小项目可以跳过
✓ .gitignore：已忽略 .devflow/runtime/

✓ 表示正常，! 表示警告，✗ 表示错误。有 ✗ 时退出码为 1，每个问题下面都附有修复命令。知识页为空的警告可以先不管，见可选：生成知识页。

如果出现以下问题

  • ! project.yaml：没有声明验证命令：回到第 3 步。不声明验证命令时，验证结果永远是 unknown，变更无法归档。
  • ✗ hook：…不存在：devflow 的安装位置变了，重新运行 devflow init。
  • ✗ hook ../backend：没有 pre-commit hook：声明了 code_roots 之后没有重新运行 devflow init。
  • ✗ Agent 文件…不一致：运行 devflow update。

5. 提交

终端
git add -A && git commit -m "启用 DevFlow"

预期输出中会有一行，表示提交门禁已经生效：

输出
✓ devflow check 通过

使用 Codex 时，第一次在项目里打开 Codex 要选择信任该项目，.codex/rules/ 才会加载。

走一遍完整的变更

下面以一个最小的需求为例：给 math.js 新增 subtract(a, b)。每一步都标明由谁来做。

第 1 步：提方案Agent

在 Agent 里说：

用 devflow-propose 提一个变更：在 math.js 中新增 subtract(a, b)，返回 a 减 b。

Agent 信息不足时会先问你，然后读相关代码和当前规范，运行 devflow new <id> 生成目录，写好方案，最后运行 devflow validate 和 devflow render。这一步 Agent 不会改业务代码。

Agent 生成的变更目录如下：

输出
.devflow/changes/2026-11-08-add-subtract/
├── change.yaml            标题、影响路径、方案要点、待你拍板的事项
├── proposal.md            为什么、改什么、影响、不做什么
├── specs/math/spec.md     规范增量：本次对系统行为契约的增、改、删
├── design.md              技术方案与流程图
└── tasks.yaml             任务、依赖与验收条件

其中 tasks.yaml 是后面验收的依据，每条验收条件都要写清楚怎么证明：

YAML
schema_version: 2
tasks:
  - id: T1
    title: 实现 subtract 并补测试
    acceptance:
      - id: AC1
        text: subtract(5, 3) 返回 2
        method: automated      # automated：由验证命令证明；manual：由人确认
        check: unit-tests      # 引用 project.yaml 中的 verify.name

change.yaml 里的 summary（方案要点，最多 7 条）和 decisions（需要你拍板的事项）显示在审查页前两个面板：拍板事项在首屏，方案要点紧接其后。

YAML
summary:
  - 新增 subtract(a, b)，返回 a 减 b
decisions:
  - question: 非数字输入怎么处理？
    options: [抛 TypeError, 不处理]
    recommend: 不处理

验证：Agent 最后会给出 render 的结果，然后在后台运行 devflow wait <id> 等你批准。

输出
✓ /path/to/project/.devflow/runtime/rendered/2026-11-08-add-subtract.html
  内容哈希：sha256:79445fe7ed97bef5475cec4400d48d5e7ece7c1f033f7997691a9db2a89bc446
  审查后由人批准：在审查台（devflow review）里点「批准此版本」，或在自己的终端运行 devflow approve 2026-11-08-add-subtract
  等待批准：devflow wait 2026-11-08-add-subtract

第 2 步：审查人

在你自己的终端里启动审查台：

终端
devflow review
输出
审查台已启动：http://127.0.0.1:52341/3f9c…/
保持这个终端打开；按 Ctrl+C 结束。地址里带有本次启动的令牌，不要贴给 Agent。

浏览器会自动打开变更列表，需要你操作的排在前面。点开变更就是审查页。审查页直接从方案文件生成，没有经过模型改写。

「工作节点」一列写着每个变更走到了哪一步。带蓝点的节点轮到你操作，灰点的节点由 Agent 在做：

工作节点含义谁来做
写方案中方案还没通过 devflow validateAgent
待你批准方案已校验通过，或批准后方案有改动你
待开工已批准，Agent 还没运行 devflow apply --startAgent
实现中（任务 x/y）已开工，还没验证，或验证后又改了代码Agent
补证据中验证通过，但还有任务缺验收证据，或证据已失效Agent
修复中 / 待重新验证验证没通过；或任务都做完后又改了代码Agent
待你确认 N 条有 N 条人工证据等你确认你
归档准备中验证通过，但知识页检查（devflow wiki lint）有错误Agent
待你归档可以归档了你

归档过的变更列在首页下方「已归档」里，最新的在前。点进去是只读页，有方案原文、拍板结论和事件时间线，没有任何操作按钮。

审查台不会定时刷新页面。它在后台每 5 秒查一次状态，有变化时页面上出现「有新进展，点此刷新」，你点了才刷新。刷新后页面会回到原来的滚动位置，展开过的面板保持展开。批准、确认之后的自动刷新也一样。

变更页的布局：

  • 顶部操作栏固定在页面顶部，滚动到哪里都看得到。栏里依次是：返回首页、当前状态、要你做的操作按钮、发送批注、Agent 是否在等待。
  • 左侧目录列出所有面板，标题下面一行是面板的状态，例如「与上次批准相同」。点一下就跳到那个面板；面板是折叠的会先展开。你看到哪个面板，目录里就高亮哪个。窗口宽度小于 1024 像素时目录隐藏。
  • 首屏「进展与待办」只放三样：进度条（方案、批准、实现、验证与证据、归档，当前段下面写着工作节点）、「要你做什么」一句话，以及待拍板事项。每个待定事项给出选项和推荐项。
  • 「方案要点与影响范围」紧接在首屏下面，默认展开。
  • 批注记录在页面最后，列出这个变更发过的全部批注：时间、面板、引用原文、意见，以及 Agent 是否已读。没发过批注时没有这个面板。

离线审查页（devflow render 生成的文件）的首屏也是这个结构，但没有顶部操作栏、左侧目录和批注记录。

细节面板默认折叠，需要时展开：

面板内容
A 提案为什么、改什么、影响、不做什么
B 规范增量新增（绿）、修改（黄）、删除（红）的需求，每条需求附场景表（WHEN / THEN）
C 设计技术方案与流程图
D 任务与依赖每个任务的验收条件和依赖图
E 被审文件与内容哈希验证命令、每个文件的哈希，以及可以直接复制的批准命令

重点看三处：

  1. 验收条件能不能真正被验证？automated 的条件引用的是哪个验证命令？
  2. affected_paths 有没有覆盖要改的代码？
  3. "不做什么"是否符合你的预期？

要修改时，在审查页上选中要说的那段文字，点浮出来的「批注」，写下意见并保存。可以攒多条，操作栏会显示「发送批注（N 条）」，点开可以删掉不要的，再点「发送」。批注直接送到在后台等待的 Agent。devflow wait 收到后退出，打印引用原文和你写的意见。Agent 照此改方案、重新生成审查页，哈希也随之变化。

  • 操作栏写着「Agent 正在等待」时，批注马上送达；写着「没有 Agent 在等待」时，批注留到它下次运行 devflow wait。
  • 想对整个面板提意见，点面板标题旁的「批注」，引用原文记为「整个面板」。
  • 选区不能跨两个面板。没发送的批注在刷新页面后还在。还有没发送的批注、或对话框开着时，点「有新进展，点此刷新」不会刷新，先发送或删掉批注。
  • 审查台只有「批注」这一种提意见的方式，渲染器自带的「回复」、标注模式和面板评论框在这里不显示。
  • 还有没发送的批注时点「批准」会被拦住：先发送或删掉。
  • 也可以直接在对话里告诉 Agent 改哪里。

不想开审查台时，也可以直接用浏览器打开 render 生成的 HTML 文件。它离线可用，但不能批准，也不能发送。点页面右上角「批注」，意见会被整理成一段文字，复制后粘贴回对话即可。

第 3 步：批准人

在审查页里给每个待定事项选好结论（默认是推荐项），点「批准此版本」。页面显示「现在不需要你操作，等 Agent 继续」，后台的 devflow wait 随即退出，Agent 接着开工。你选的结论记入批准记录，Agent 运行 devflow resume 时会看到。

改方案后重新批准：页面多一个「批准差异」面板，只列改动的行；没改的面板标题上注明「与上次批准相同」，可以不再看。验收条件和代码都没变的证据、任务完成记录会沿用，不用重做。

也可以不用审查台，复制审查页 E 面板末尾的命令，在你自己的终端里运行：

终端
devflow approve 2026-11-08-add-subtract --hash 79445fe7ed97

--hash 至少要有 12 位。它和当前内容一致时直接批准，不会再让你输入 y。预期输出：

输出
变更：2026-11-08-add-subtract
基线：a1b2c3d  批准人：你的名字
内容哈希：sha256:79445fe7ed97…
被审文件：
  .devflow/changes/2026-11-08-add-subtract/change.yaml
  …
✓ 已批准 2026-11-08-add-subtract
下一步：在 Agent 里说"用 devflow-apply 实现变更 2026-11-08-add-subtract"

只有看到 ✓ 已批准 才算成功。

不带 --hash 时，终端会列出同样的信息并要求确认。核对哈希和审查页一致后，输入 y 并回车。

如果批准不成功

提示原因与处理
--hash 与当前内容哈希不一致，未批准审查之后方案又被改过，或者命令没复制完整。重新 render，从新页面复制命令
approve 只能由人在交互终端中运行命令在非交互环境中运行，例如被 Agent 代为执行、在编辑器任务面板里运行或经过管道。请在普通终端窗口里运行
✗ 未批准：… 状态仍为 draft确认时没有输入 y。重新运行
未配置 git user.name运行 git config user.name "你的名字"，批准人取自这里

第 4 步：实现并验证Agent

在 Agent 里说：

用 devflow-apply 实现变更 2026-11-08-add-subtract。

Agent 会先记录开工：

终端
devflow apply 2026-11-08-add-subtract --start
输出
✓ 2026-11-08-add-subtract 已开工（基于 a1b2c3d）

然后写代码和测试，运行验证命令：

终端
devflow verify 2026-11-08-add-subtract --json
JSON
{
  "result": "pass",
  "checks": [{ "name": "unit-tests", "log_hash": "sha256:…", "exit": 0, "ms": 412, "log": ".devflow/runtime/verify/…" }],
  "run_id": "6f1c…"
}
注意

下一步记录证据时要用到 run_id，它只在 --json 输出里出现。不加 --json 时，输出是 ✓ unit-tests 退出码 0 0.4s，后面跟一行"配置检查结果"。

Agent 发现方案本身有问题时，会停下来告诉你，而不是自己改方案。改方案会让批准失效，需要你重新批准。

第 5 步：记录验收证据Agent，人工项由人确认

测试通过，不等于验收条件被覆盖了。每条验收条件都需要一份证据，说明它是由哪个测试、哪条断言证明的，并从验证日志里原样摘一行输出。Agent 写一个 JSON 文件：

JSON
{
  "task": "T1",
  "acceptance": "AC1",
  "kind": "automated",
  "summary": "subtract(5, 3) 返回 2",
  "verify_run": "6f1c…",
  "check": "unit-tests",
  "test": "test/math.test.js",
  "assertion": "assert.equal(subtract(5, 3), 2)",
  "log_quote": "✔ subtract(5, 3) 返回 2",
  "artifacts": []
}
终端
devflow evidence add 2026-11-08-add-subtract --file AC1-evidence.json

命令会输出记录下来的证据，其中包含 evidence_id。审查页的验收矩阵有四列：验收条件、状态、依据、说明。依据列写测试文件和日志原文；人工项写实际观察。

自动证据引用的验证要满足三个条件：在本轮批准之后，基于当前代码版本，指定检查通过。否则会被拒绝。

log_quote 可选，但建议填：devflow 会核对这行字确实出现在那次验证的日志里，审查页的验收矩阵在「日志核对」一列显示「已核对」；没填的显示「未核对」。日志里没有这行字、日志被改过或已丢失时，证据会被拒绝。

人工验收项（method: manual）的证据，把 kind 改成 manual，并填写 procedure（怎么操作）、expected（预期）、observed（实际看到的）。Agent 记录之后在后台运行 devflow wait <id>，由你确认：在审查台打开该变更，点「确认人工证据」，勾选要确认的项；或者在自己的终端运行：

终端
devflow evidence confirm 2026-11-08-add-subtract <evidence-id>

所有验收条件都有有效证据后，Agent 标记任务完成：

终端
devflow task done 2026-11-08-add-subtract T1
输出
✓ T1 已完成；任务 1/1

状态与下一步

状态不存盘，每次都由变更文件、events.jsonl 和 git 现算。查看状态：

终端
devflow status                 # 所有进行中的变更
devflow status <id>            # 一个变更
devflow status --all           # 同时列出已归档的变更
devflow resume <id>            # 一个变更：状态、证据缺口和下一条命令
输出
2026-11-08-add-subtract  draft  任务 0/1  尚未批准  ← 待你批准
2026-11-07-role-access  applying  任务 1/3  还有 2 个任务未完成  ← Agent 进行中 · 停滞 30 小时

行尾写着轮到谁。已批准或已开工的变更，最后一条记录超过 24 小时时标出「停滞 N 小时」（满 48 小时按天算），审查台的列表里也会显示。阈值在 project.yaml 里用 stale_hours 调整。

状态含义下一步
draft尚未批准，或者批准后被审文件被改过人审查后 approve
rebase_required已批准、未开工，但批准后有提交改动了 affected_paths，或者同一能力的规范变了人重新评估方案，必要时让 Agent 修改，再 approve
approved已批准，可以开工Agent 用 devflow-apply 实现
applying已开工；任务未完成、证据失效，或者验证之后代码有改动Agent 继续实现，或者重新 verify 并补证据
needs_fix最近一次验证结果为 fail 或 unknown看验证日志修复后重新 verify
ready_to_archive任务全部完成，证据有效，且验证通过的就是当前代码人提交代码 → Agent 做归档准备 → 人 archive
archived已归档—

规则：

  • 改方案就要重新批准：批准后改动任何被审文件或 project.yaml，状态回到 draft。
  • 重新批准就是新的一轮：要重新 apply --start 和 verify。验收条件（文本、方式、检查命令）和代码都没变的证据与任务完成记录沿用，其余要重做。
  • unknown 不算通过：命令无法运行、超时（单条 30 分钟）、没有声明命令、验证期间工作树变化，结果都记为 unknown。
  • 一个工作树同时只能开工一个 v2 变更。要并行做多个变更，用独立的 git worktree。

可选生成知识页

知识页（.devflow/knowledge/pages/*.md）记录代码"现在是怎样"，每条事实都带源码出处。在 Agent 里说：

用 devflow-scan 为本项目生成知识页。

Agent 会按业务模块写页面，并运行 devflow wiki lint，直到没有错误。

注意

小项目可以跳过这一步。在一个 25 个文件的演示项目上评测，有没有知识页，回答准确率相同，而且有知识页时每题多用约 25% 的轮数。知识页适合记录代码里看不出来的内容，例如设计原因和历史变更；也适合 Agent 读不完代码的大项目。

可选本地使用记录

init 之后，项目默认在本地记录 devflow 命令的使用情况：命令名（白名单内）、结果、原因码和耗时。不记录完整参数、输出、环境、用户名或源码，也不上传。原始记录保留 30 天，反馈保留 90 天，报告保留 180 天。

终端
devflow usage configure --off             # 关闭
devflow usage configure --on              # 打开
DEVFLOW_USAGE=off devflow status          # 只对这一次命令关闭
devflow usage report --since 2026-11-01   # 本地报告
devflow usage feedback <id> --file feedback.json
devflow usage export --since 2026-11-01 --out summary.json
devflow usage prune --before 2026-10-01

反馈文件格式为 {category, impact, note, related_invocation?}，其中 category 取 blocked、confusing、false-positive、missed-defect 或 other。note 是自由文本，默认不会出现在聚合导出里；不要在里面写凭据。

关闭记录或记录写入失败，都不影响命令本身的退出码。

可选改进候选与评测

同一类问题出现至少 3 次，会生成一个去重后的改进候选。候选只会生成一份待补全的提案，不会自动审批或实施。

终端
devflow improve list
devflow improve draft <candidate-id> <change-id>
devflow eval run --suite workflow --out regression.json
devflow eval compare baseline.json regression.json
devflow improve resolve <candidate-id> --report comparison.json

故障评测在临时仓库里运行。标记为 improved 有三个条件：每个任务每个版本至少跑 5 次，关键结果不退化，目标中位指标至少下降 10%。即使满足，也不代表统计显著。真实 Agent 评测需要显式启动，可能消耗账号额度。

可选继续使用 v1 格式

0.2.0 新建的变更默认是 v2 格式（schema_version: 2，验收条件带证据）。旧的 v1 变更可以继续使用。要显式创建 v1 格式：

终端
devflow new <id> --schema 1

已有 v2 变更的项目，不能再用旧版 CLI 往里追加事件。

文件格式参考

project.yaml人维护

YAML
schema_version: 1
verify:                  # devflow verify 只运行这里的命令
  - name: unit-tests     # 不能重复
    run: npm test        # 用 sh -c 执行
    cwd: .               # 可选，相对仓库根目录
exclude:                 # 知识页和证据不得引用的文件，规则同 .gitignore
  - ".env*"
  - "**/*.pem"
  - "**/*.key"
  - "**/node_modules/**"
enforce: warn            # warn | strict：暂存了未开工变更的代码时，警告还是拒绝提交
code_roots: ["../backend"]   # 可选：代码所在的 Git 仓库，相对本仓库根
stale_hours: 24          # 可选：最后一条记录超过多少小时算停滞，必须是正数

这个文件计入批准哈希：改了它（包括 stale_hours），进行中变更的批准都会失效。

change.yaml

YAML
schema_version: 2
min_cli_version: 0.2.0
title: 新增减法函数
affected_paths:          # 本变更会改动的代码（glob），不能写 .devflow/ 下的路径
  - math.js
  - test/**
summary:                 # 方案要点，最多 7 条，显示在审查页首屏下方的「方案要点与影响范围」
  - 新增 subtract(a, b)
decisions:               # 需要人拍板的事项，没有就留空；recommend 必填，必须是选项之一
  - question: 非数字输入怎么处理？
    options: [抛 TypeError, 不处理]
    recommend: 不处理

affected_paths 有两个用途：批准后有提交改动了这些路径时，状态变为 rebase_required；提交未开工变更的这些文件时，门禁会警告。代码在 code_roots 的仓库里时，路径以该项开头，例如 ../backend/src/**。

proposal.md

写四节：## 为什么、## 改什么、## 影响、## 不做什么。不能只有标题没有正文。超过 3 句的段落，validate 会给出警告。

规范增量 specs/<能力>/spec.md

Markdown
## ADDED Requirements

### Requirement: 减法
系统 SHALL 导出 subtract(a, b)，返回 a 减 b 的结果。

#### Scenario: 整数相减
- WHEN 调用 subtract(5, 3)
- THEN 返回 2

## MODIFIED Requirements
### Requirement: <当前规范中已有的名称>
（这条需求修改后的全文）

## REMOVED Requirements
### Requirement: <当前规范中已有的名称>
**Reason**: 删除原因
  • 能力名（目录名）只能用小写字母、数字、连字符。
  • 每条新增或修改的需求都必须含 SHALL、MUST 或"必须"，并且至少有一个 #### Scenario:。
  • 新能力只能用 ADDED，可以加一节 ## Purpose 说明这个能力是什么。
  • MODIFIED 和 REMOVED 里的名称，必须和当前规范完全一致。
  • 不改变对外行为的变更（例如纯重构）可以不写规范增量。validate 只会提醒，不算错误。

tasks.yaml（v2）

YAML
schema_version: 2
tasks:
  - id: T1
    title: 实现 subtract 并补测试
    acceptance:
      - id: AC1
        text: subtract(5, 3) 返回 2
        method: automated        # automated | manual
        check: unit-tests        # automated 必填，引用 verify.name
  - id: T2
    title: 更新使用说明
    depends_on: [T1]
    acceptance:
      - id: AC2
        text: README 示例可以照抄运行
        method: manual
  • 任务 id 以字母开头，不能重复。depends_on 引用的任务必须存在，依赖不能成环。
  • 验收条件的 id 在整个变更内唯一。
  • 不要写进度字段（如 status、done）。进度记在事件日志里；写在这个文件里的话，每勾选一次任务，批准就会失效一次。
注意

在 0.2.0 中，devflow new 生成的 tasks.yaml 骨架里，注释示例仍是 v1 写法（acceptance: [字符串]）。请按上面的 v2 对象格式写。

流程图写在代码块里：

  • 可用的图：flow、sequence、tree、er。
  • 普通代码块只写语言名，例如 ```java。

字段automatedmanual说明

events.jsonl

每行一个事件，记录批准、开工、验证、证据、任务完成和归档。只能由 devflow 命令追加。已提交的行被改动或删除时，提交会被门禁拒绝。

  • verified_commit 要加引号：1234567 这样的短哈希不加引号，会被 YAML 当成数字读取。
  • symbol 写成 类名 或 类名#方法名，必须和源码里的文字一致。

devflow wiki lint 在以下情况报错误：

  • frontmatter 缺失或字段不合法
  • 引用的文件不存在、符号找不到或行号越界
  • 引用了 exclude 中的文件
  • index.md 漏列页面，或列了不存在的页面
  • 正文链接指向不存在的目标

  • 引用的文件在 verified_commit 之后有改动
  • 正文引用了没列入 sources 的文件
  • 一个知识页都没有

devflow init 为每个 Agent 安装五个技能。

技能什么时候用典型说法
devflow-propose新功能、行为修改、修复，先出方案"用 devflow-propose 提一个变更：……"
devflow-apply实现已批准的变更，并验证、记录证据"用 devflow-apply 实现变更 <id>"
devflow-archive验证通过后、归档前，更新知识页"用 devflow-archive 为变更 <id> 做归档准备"
devflow-scan生成或修复知识页"用 devflow-scan 生成知识页"
devflow-ask带出处回答关于项目的问题"X 在哪里实现？"（不说技能名也会用到）

提交门禁

pre-commit hook 运行 devflow check --staged。CI 中可以运行 devflow check，检查工作树。声明了 code_roots 时，代码仓库的 hook 运行 devflow check --staged --project <本仓库>，只检查「暂存了未开工变更的代码」这一条。

规则结果
.devflow/ 下的文件格式错误拒绝提交
.devflow/specs/ 和 specs.lock 不符（手改、手加、手删）拒绝提交
events.jsonl 中已提交的行被修改或删除拒绝提交
暂存了某个变更 affected_paths 内的代码，而该变更还没开工警告；enforce: strict 时拒绝
暂存了已开工变更的代码，但它的 events.jsonl 没有暂存或不是最新警告，提示 git add .devflow/changes/<id>
有已开工的变更时，暂存了不属于任何进行中变更、也不在 .devflow/ 下的文件警告，列出这些文件
知识页有问题（过期、引用失效等）警告

规范、事件日志、批准快照和证据附件，按暂存区的内容检查。方案格式和业务状态仍然按工作树计算，所以用 git add -p 部分暂存时，请核对相关文件是否都暂存了。

紧急情况可以用 git commit --no-verify 跳过本地门禁，CI 中的检查仍然有效。

安全模型

DevFlow 防的是 Agent 的失误和越级：跳过审批、自己判定通过、手改规范。它不防恶意篡改，有写权限的 Agent 理论上能改任何文件。防线有三层：

  1. 人专属命令要求交互终端：approve、archive、evidence confirm、review 在非交互终端中直接拒绝。审查台只监听 127.0.0.1，地址里带每次启动随机生成的令牌，不要把地址贴给 Agent。在 Codex 下，这一层可以被绕过（见选择你的 Agent）。
  2. Agent 侧的禁止规则：Claude Code 用 .claude/settings.json 禁止运行 approve 和 archive，并禁止直接编辑 .devflow/specs/ 和 events.jsonl；Codex 用 .codex/rules/devflow.rules。
  3. git 门禁和代码审查：批准记录随 events.jsonl 进入提交。审查代码时，能看到谁在何时批准了哪个变更。

另外：

  • verify 只运行 project.yaml 中的命令，而 project.yaml 计入批准哈希。
  • 审查页离线生成，不加载任何外部资源，也不执行方案里的 HTML 或脚本。
  • 知识页和证据都不能引用 exclude 中的文件。

常见问题与排错

提交后状态从 ready_to_archive 变回了 applying
提交本身不会造成这种情况。原因是验证之后有文件被改过，包括文档。运行 devflow resume <id> 查看原因，然后重新 verify 并补齐证据。

状态是 rebase_required
批准之后，有提交改动了 affected_paths 里的文件（包括 code_roots 仓库里的提交）；或者别的变更改了同一能力的规范。让 Agent 检查方案是否仍然适用，必要时修改，然后重新批准。

archive 被拒："规范 X 在本变更批准后被修改过"
另一个修改同一能力的变更先归档了。让 Agent 根据最新规范更新本变更的规范增量，然后重新批准、重新验证。

archive 被拒："知识页有 N 个错误"
运行 devflow wiki lint 查看，或者让 Agent 用 devflow-scan 修复。

提交被拒："内容与 specs.lock 不符"
有人手改了 .devflow/specs/。用 git restore <文件> 撤销，新加的文件直接删除。要改规范，请新建一个变更并归档。

提交被拒："事件日志的已提交内容被修改或删除"
用 git restore .devflow/changes/<id>/events.jsonl 恢复。

.DS_Store 或编辑器临时文件让批准失效、提交被拒
devflow 只看 git 会跟踪的文件。出现这类问题，说明这些临时文件没有被忽略。把它们加进 .gitignore：

终端
echo '.DS_Store' >> .gitignore

render 报"审查页内容有 N 处不允许的写法"
错误信息里有文件名和行号。把 html、svg 代码块改成 flow 等图形块，去掉代码块属性和图片。

知识页报 verified_commit ... 必须是提交哈希
给哈希加上引号：verified_commit: "1234567"。

Codex 没有拦截 devflow approve
第一次在项目中使用 Codex 时，要选择信任该项目，.codex/rules/ 才会加载。即使加载了规则，交互终端检查在 Codex 下仍可能被绕过。

升级 devflow

  1. 重新打包，并全局安装新版本。
  2. 在每个已启用 DevFlow 的项目里运行 devflow update，重新生成技能和说明段落。手工改过的技能文件会被覆盖。
  3. 运行 devflow doctor，确认 hook 和 Agent 文件都是最新的。

已知限制

  • 规范从变更中逐步积累：.devflow/specs/ 一开始是空的，只随着归档增长。DevFlow 不会从现有代码自动生成规范，因为那样的规范没有经过审核。
  • 审查台是本地临时服务：只在你运行 devflow review 的终端开着时可用，关掉终端就停止。
  • 不自动提交、推送或部署：这些都由人决定。
