## 三方各做什么

```kv cols=1
* 人: 审查方案、批准、确认人工证据、提交代码、归档、维护验证命令
Agent: 读代码、写方案、写代码与测试、记录证据、更新知识页
tenon 命令: 校验格式、绑定批准哈希、计算状态、运行验证命令、合并规范、提交时把关
```

Tenon 自己不调用模型。Agent 用 Claude Code 或 Codex。

## 一次变更的时间线

```timeline v
第 1 步 | 提方案 | Agent：tenon-propose
*第 2 步 | 审查 | 人：tenon review 打开审查台
*第 3 步 | 批准 | 人：在审查台点「批准此版本」
第 4 步 | 实现并验证 | Agent：tenon-apply
第 5 步 | 记录验收证据 | Agent 记录并摘日志原文，人在审查台确认人工项
*第 6 步 | 提交代码 | 人
第 7 步 | 归档准备 | Agent：tenon-archive
*第 8 步 | 归档 | 人：在审查台点「归档」
```

## 谁在什么时候动手

```sequence num
participants: 人, Agent, tenon
人 -> Agent: 提出需求
Agent -> tenon: new、validate、render
tenon --> 人: 审查台列出待批准
Agent -> tenon: wait（后台等）
人 -> tenon: 审查台里批准
== 实现 ==
Agent -> tenon: apply --start
Agent -> tenon: verify --json
tenon --> Agent: run_id
Agent -> tenon: evidence add、task done
== 收尾 ==
人 -> 人: 提交代码
Agent -> tenon: wiki lint
人 -> tenon: 审查台里归档
```

## 状态怎样流转 {span=2}

```flow LR
(draft) -> approved: 人批准
approved -> applying: apply --start
applying -> *ready_to_archive: 验证通过且证据齐全
applying -> needs_fix: 验证 fail 或 unknown
needs_fix -> applying: 修复后重新验证
ready_to_archive -> applying: 验证后又改了文件
ready_to_archive -> (archived): 人归档
approved --> rebase_required: 影响路径或规范变了
rebase_required --> draft: 修改方案
```

状态不存盘，每次都由变更文件、事件日志和 git 现算。批准后改动任何方案文件或 `project.yaml`，状态都会回到 `draft`。

## 三条要记住的规则

```callout warn 改方案就要重新批准
被审文件和 project.yaml 计入批准哈希。改动后要重新批准、开工和验证；验收条件与代码都没变的证据自动沿用。
```

```callout warn unknown 不算通过
命令无法运行、超时、没有声明命令、验证期间文件变化，结果都是 unknown。
```

```callout info 文档在验证之前写完
验证结果绑定当时的文件内容。验证后改任何文件，都要重新验证并重新记录证据。
```

## 三层防线

| 防线 | Claude Code | Codex |
| --- | --- | --- |
| 人专属命令要求交互终端，并拒绝 Agent 环境 | ok 有效 | ok 靠环境变量检查 |
| Agent 侧禁止规则 | ok 已实测拦截 | warn 信任项目并确认钩子后生效 |
| git 门禁与代码审查 | ok 有效 | ok 有效 |

Tenon 防的是失误和越级，不防恶意篡改。
