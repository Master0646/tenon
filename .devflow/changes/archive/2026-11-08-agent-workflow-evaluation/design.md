## 实验方法
- 比较对象为 DevFlow 实现前后版本，Agent 模型、演示项目、任务、初始故障、工具权限和评分器相同；不是把前后版本与原生 Agent 两种对照混在一起。
- 在 eval/protocol.yaml 冻结代码完整提交号、演示项目树哈希、运行器版本、可用工具、模型标识、预算、评分器版本和随机种子支持情况。
- 基线不支持新命令时，使用两版均有的业务操作和冻结的外部观察器；不能把“没有新命令”直接记为业务漏检。
- 每个任务每个版本至少五次，共至少 30 次真实运行，基线和候选交替执行；每次使用全新临时项目和新会话。
- 原始输出保存在 eval/results/agent-workflow-comparison/，公开报告只展示经核对且不含秘密的摘要；每个样本可关联运行时间、版本和原始记录哈希。
- 评分依据实际业务断言：配置值依据、普通用户直接请求权限接口及数据不变、新会话对未完成验收的定位与下一步。
- 完成率、漏检、误拦、人工介入、工具调用和耗时分别报告；拿不到 token/费用或人工介入数据就保持 unknown。
- 环境无法完成时保留 unknown 与原因，不能将前端构建/真实接口验证降为静态检查；停止的样本照实保留，不悄悄补跑。
- 付费模型运行前明确模型及账号权限；每次最多 100 次调用、30 分钟、零隐式重试；用户可随时停止，停止后只汇总已有证据。

## 闭环演示
```flow LR
真实反馈 -> 本地报告 -> 优化候选 -> 正式提案 -> 人工批准 -> 修复实现 -> 固定回归 -> 真实对照 -> 候选结果回填
```
- 使用隔离演示仓库；人的批准仍由人在自己的终端完成，运行器不伪造生产人的事件。
- 演示中的修复必须是具体问题及独立可审查变更；可以修复评测夹具内的故障，不以演示为理由修改生产规则。
- 关联 candidate_id、报告哈希、提案、修复提交、回归案例与最终比较报告，形成可追踪链路。

## 结论与停止条件
- 使用既有 compareReports 的判据，不在看到结果后调整协议或放宽阈值。
- 报告 improved、regressed 或 inconclusive，并展示每任务样本数和分布；本批 improved 不代表统计显著。
- 任一关键任务缺失有效样本时不得将本案全部标记完成；真实收益未确认时保持证据不足。
- 本案不新增 CLI 业务行为，所以不包含 delta spec；若发现需要修复生产功能，另提独立行为变更。
